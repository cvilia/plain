>
> ⚠️ **本节曾把上述表记为「UI 入口为占位」或「未落地」，与代码不符，已按 `plain/lib` 实况校正。** 校正依据是 `budget_repository.dart`、`recurring_repository.dart`、`budget_page.dart`、`recurring_scheduler.dart`、`rule_engine.dart`、`merchant_learner.dart` 等文件的实际存在，而非设计推测。**由此，§1 原「只有 3 张是权威数据」的表述应理解为「3 张 V1.0 业务主表 + 5 张已实现、功能归属后续版本的权威表」**，共 8 张权威表。

**三条不可违背的规则**（后文逐一给依据）：

1. **派生值不进权威表**。余额、统计聚合都不落权威表的列——派生值一旦进入同步范围，多端各自增量维护必然漂移。
2. **数据库只约束「永不变的不变量」，会变的产品策略放在领域层**。`amount_cents > 0` 是语义不变量，进 DDL；「金额上限是多少」是产品策略，不进 DDL（当前实现值为 **99,999,999.99 元**，见 §7.8）。
3. **后补需要触碰历史行数据的，必须在 V1.0 落地**。这是对《04》§5.3「功能可后置，数据形态不可后置」的可操作化——判据不是「这个功能现在用不用」，而是「以后补的时候要不要改已存在的行」。

**三条规则直接推出了四个反直觉的结论**：转账用单行而非双行（§7.1）、账户余额不存列（§7.2）、统计按日粒度且因此**取消了 PRD 里那个「重度操作」提示**（§7.3）、change_log 必须存变更前后值（§7.4）。

## 2. 设计判据：什么必须现在做，什么可以后补

《04》§5.3 给出了正确方向（「功能可后置，数据形态不可后置」），但没给出可判定的边界。本文档把它落成两条可操作的判据：

| 判据 | 结论 | 本项目的例子 |
|---|---|---|
| **后补是否需要改写已存在的行数据？** | 需要 → **V1.0 必须落地** | 主键类型（UUID v7）、审计字段（软删除 / revision / device_id / base_revision）、change_log 的 `payload`（祖先内容事后无法回填）、日期粒度（聚合表粒度改变即需重算全部历史） |
| **后补是否只需追加列 / 追加表，且追加后有合理默认值？** | 只需追加 → **可以后补** | 布尔标志（不计入收支、报销）、信用卡属性组、标签关联表、冲突副本表、book 实体表 |

被这条判据**排除**在 V1.0 之外的（明确记下来，避免重复讨论）：

- `tags` / `transaction_tags`：标签是**多对多**关系，正确形态是关联表。V3.0 直接新增两张表即可，属纯追加、零数据改写。**反而不该在 V1.0 往 transactions 里塞一个 JSON 列**——那样就要做「JSON 拆表」的数据迁移，把一个便宜的追加变成了昂贵的改写。
- `books` / `conflict` / `sync_meta` / `settings` 权威表：V2.0 随版本迁移脚本新增。
- **V3.0 方法论与新实体表**（`Rule` / `ReimburseSheet` / `SavingsGoal` / `LoanPlan` / `Holding` / `MerchantRule`）：全部属纯追加，逐表清单与建表理由见 §10.1。

> **实测偏差**：`budgets` / `recurring_rules` 两张表按判据本可推迟，但**代码在 V1.0 就已完整实现**（含实体 / 仓储 / 用例 / UI，见 §1）。这是实现层面「一次到位」的取舍：一次建表并贯通全链路，换 V2.0 不动 schema。判据本身不变，仅清单与代码对齐。
>
> ✅ **判据内项已全部落列（2026-10-15 复核）**：`transactions.split_role` / `parent_id` / `reimburse_status` / `reconciled_at`、`categories.is_rigid` 按判据**属于「V1.0 必须落地」**（后补要触碰历史行）——**代码中已全部落列**（v4 / v10 / v11 迁移），判据与实现之间已无字段级缺口。详见 §5.1 / §5.2 与 §9.1。
>
> ✅ **口径缺口已修复**（见 §7.3 与 §11 的 C11）：`daily_stats` 的写入门原只判 `type` 不判 `source`，导致对账调整被计入日统计，与 PRD G-2 口径不符。**2026-10-15 已修**：`LedgerEntry.countsInOutflow` / `countsInCategoryStats` 均加 `source != EntrySource.reconcile` 门，`AccountRepositoryImpl.reconcile()` 直写分支已删，回归 `test/reconcile_stats_test.dart`。修它未涉及任何 schema 变更。

## 4. 通用约定

### 4.1 类型与单位

| 项 | 约定 | 理由 |
|---|---|---|
| 主键 | `TEXT`，UUID v7（26 字符，小写 Crockford Base32） | 时间有序（B-tree 插入局部性好、分页稳定）+ 全局唯一（V2.0 多端合并必需）。主键类型变更是灾难级迁移，**V1.0 定死** |
| 金额 | `INTEGER`，单位「分」，**恒为正** | 浮点误差在记账产品中不可接受（《04》§5.1）。方向由 `type` 表达，不靠负号 |
| 时间 | `INTEGER`，UTC 毫秒；展示层换算本地时区 | 跨时区与夏令时正确性的前提（《06》D6） |
| 记账日 | `TEXT`，`'YYYY-MM-DD'`，**写入时的本地日** | 仅用于派生统计；「今天花了多少」必须按本地日，不能按 UTC 日 |
| 枚举 | `TEXT`，存稳定英文标识，**不加 CHECK 约束** | 见 §7.7 |
| 布尔 | `INTEGER`，`0` / `1` | SQLite 无原生布尔 |
| 可空 | 显式声明；业务上「无值」与「未填」不区分 | 避免三态语义 |

### 4.2 统一审计字段块（八张权威表逐字相同）

```sql
  created_at    INTEGER NOT NULL,            -- 创建时刻，UTC 毫秒
  updated_at    INTEGER NOT NULL,            -- 最后修改时刻，UTC 毫秒
  deleted_at    INTEGER NULL,                -- 软删除时刻；NULL = 存活
  revision      INTEGER NOT NULL DEFAULT 1,  -- 实体版本号：每次成功变更 +1
  device_id     TEXT    NOT NULL,            -- 最后写入设备
  base_revision INTEGER NOT NULL DEFAULT 0   -- 本次修改所基于的版本（3-way merge 祖先指针）
```

**语义**：新建实体 `revision = 1`、`base_revision = 0`（0 表示「无祖先」）；每次更新时 `revision++`，并把**更新前**的 `revision` 写入 `base_revision`。V2.0 的三方合并以此定位共同祖先（《04》§6.3）。

> **对《04》§5.3 的措辞精确化**：《04》把「来源枚举」与软删除、revision 并列为「审计字段」。实际上 `source` 是**业务语义字段**（PRD §7 只对账单的「来源」提出要求），因此它只出现在 `transactions`，不构成通用审计块的一部分。这是措辞修正，不是设计变更。

### 4.3 命名与不可变性

- 表名 snake_case 复数；Dart 侧列名 camelCase，SQL 侧 snake_case——由**手写映射层**（`_fromRow` / `toRow` / 列名常量）统一转换。**业务代码里禁止手写 SQL 列名**，一律经仓储层。
- **表名与列名一经发布不可更改。** 改列名 = 一次迁移 + 全表重写 + 波及所有已发布版本的读路径，收益近乎为零。
- 允许的后续变更只有两种：**追加列**（带默认值）、**追加表 / 索引**。

> **实现说明**：数据库是**裸 `sqlite3` + 手写 DDL 与迁移**（`data/db/database.dart`），不使用 Drift 代码生成。原「由 drift_dev 的命名策略统一转换」的表述已按代码校正。改表结构必须**同步三处**：`_ddlXxx`（建表语句）、`_migrate()`（升级步）、`kSchemaVersion`（版本号）；且因 `_init()` 是**先建表再迁移**，`ALTER` 前必须先 `PRAGMA table_info` 判列存在，否则新装会报 duplicate column。

### 4.4 枚举字典（完整定义）

枚举值在 V1.0 就全部定义（PRD §7 对「来源」的要求即为此逻辑），但**标注 V1.0 的实际使用范围**——未启用的值不会被写入，只保证数据结构向前兼容。

| 枚举 | 取值 | 代码 V1.0 实际启用 |
|---|---|---|
| `EntryType` | `expense` / `income` / `transfer` / `borrow_out` / `borrow_in` / `repay_credit` / `unknown` | `expense`、`income`、`transfer` |
| `EntrySource` | `manual` / `reconcile` / `import` / `recurring` / `ocr` / `ai` / `unknown` | `manual`、`reconcile`（`recurring` 随周期引擎启用） |
| `AccountType` | `cash` / `debit` / `credit` / `loan_out` / `loan_in` / `investment` / `unknown` | **`cash`、`debit`、`credit`、`investment`（四类已在账户类型选择器开放）** |
| `CategoryKind` | `expense` / `income` / `transfer` / `unknown` | `expense`、`income` |
| `ChangeOp` | `insert` / `update` / `delete` | 全部 |
| `EntityType` | `transaction` / `category` / `account` / `budget` / `recurring_rule` | 全部（`budget` / `recurring_rule` 对应已建表） |

> **校正说明**：`AccountType` 原写「V1.0 仅 `cash` / `debit`」，与代码不符——`accounts_page.dart` 的类型选择器已开放**现金 / 储蓄卡 / 信用卡 / 投资**四项（`enabledInV1 = cash / debit / credit / investment`），`loan_out` / `loan_in` 未启用。`EntityType` 原漏 `budget` / `recurring_rule`，代码枚举中已存在。

**每个枚举必须含 `unknown` 成员，且 `unknown` 永不写入。** 它的唯一用途是「读到不认识的值时降级而不是崩溃」——V2.0 低版本 App 收到高版本数据、V3.0 导入外部文件时都会遇到。缺了这个成员，向前兼容就只能靠 try/catch，而异常会穿透分层（违反《05》B5）。

## 5. 表结构（字段级 DDL）

以下 DDL 为 SQLite 方言，**与 `data/db/database.dart` 的建表语句逐字对应**（`_ddlTransactions` / `_ddlCategories` / `_ddlAccounts` / `_ddlChangeLogs` / `_ddlAppMeta` / `_ddlDailyStats` / `_ddlBudgets` / `_ddlRecurringRules` / `_ddlRules` / `_ddlSavingsGoals` / `_ddlMerchantRules`，共 11 条）。`-- 审计字段块` 处按 §4.2 展开，**出现在 8 张权威表**（`transactions` / `categories` / `accounts` / `budgets` / `recurring_rules` / `rules` / `savings_goals` / `merchant_rules`）；`change_log` / `app_meta` / `daily_stats` 三张非权威表不带审计块。**本文档已无 `[待建]` 列**——v1.2–v1.5 曾标注的 9 个待建列（`transactions.split_role` / `parent_id` / `reimburse_status` / `reconciled_at`、`categories.is_rigid`、`accounts.credit_limit_cents` / `credit_debt_cents` / `bill_day` / `due_day`）**已全部落列**。

### 5.1 `transactions` 账单（权威）

```sql
CREATE TABLE transactions (             -- 代码实况：data/db/database.dart `_ddlTransactions`
  id            TEXT    NOT NULL PRIMARY KEY,      -- UUID v7
  book_id       TEXT    NOT NULL,                  -- 账本；V1.0 恒为 app_meta['book.default_id']
  type          TEXT    NOT NULL,                  -- EntryType
  amount_cents  INTEGER NOT NULL,                  -- 恒为正，方向由 type 决定
  currency      TEXT    NOT NULL DEFAULT 'CNY',
  category_id   TEXT    NULL,                      -- 二级分类优先；允许仅一级；未分类为 NULL
  account_id    TEXT    NULL,                      -- 支出/收入的账户；transfer 时为「转出」账户
  to_account_id TEXT    NULL,                      -- 仅 transfer 使用：「转入」账户
  occurred_at   INTEGER NOT NULL,                  -- 业务发生时刻，UTC 毫秒
  note          TEXT    NULL,                      -- 备注（PRD：联想规则的关键词来源）
  source        TEXT    NOT NULL,                  -- EntrySource；PRD §7 要求 V1.0 即存在并写入
  batch_id      TEXT    NULL,                      -- 周期生成批次（V1.0 已实现，批量撤销用）
  split_role    TEXT    NOT NULL DEFAULT 'normal', -- SplitRole：normal / parent / child（v4 落列）
  parent_id     TEXT    NULL,                      -- 子笔指向父笔（v4 落列）
  reimburse_status TEXT NOT NULL DEFAULT 'none',   -- ReimburseStatus：none / pending / reimbursed（v4 落列）
  reconciled_at INTEGER NULL,                      -- 对账逐笔勾选时刻（v11 落列，STORY-2.3）
  created_at    INTEGER NOT NULL,
  updated_at    INTEGER NOT NULL,
  deleted_at    INTEGER NULL,
  revision      INTEGER NOT NULL DEFAULT 1,
  device_id     TEXT    NOT NULL,
  base_revision INTEGER NOT NULL DEFAULT 0,

  CHECK (amount_cents > 0)                         -- 唯一进入 DDL 的业务不变量，见 §7.8
);
```

**说明**

- `book_id` 在 V1.0 是「有值但只有一个值」。保留它而不是省略，是因为加列容易、改主键难——`book_id` 参与索引与分页游标（§6），后补要重建索引与全部游标逻辑。
- 对账调整（STORY-2.1 AC3）落成一条普通账单：`source = 'reconcile'`，`type` 为 `expense` 或 `income`（差额方向）。**不设独立的对账表**——它需要完整参与统计、备份与同步，本质就是一条账单。**代码已按此实现**：对账走 `CreateEntryUseCase`（含 change_log、`daily_stats` 增量、UUID v7 主键），不再有直连 DB 的旁路写入。
- `batch_id` 是**已实现列**，用于周期规则一次生成的多笔账单打同一批次号，支持「整批撤销」。索引 `idx_entry_batch` 已建（§6）。
- **`split_role` 与 `parent_id`：`[已落列]`（v4 迁移，PRD STORY-6.2 分割交易）。** 代码实况：`_ddlTransactions` 含 `split_role TEXT NOT NULL DEFAULT 'normal'` 与 `parent_id TEXT NULL`，`_migrate()` 有对应步，`kSchemaVersion` 已推进至 **11**（§9.1）。三态语义：
  - `normal`（默认）：普通账单，本身就是完整账单。
  - `parent`（父笔）：`category_id` 置 NULL，只作账户变动与金额合计的载体；**进余额与收支统计，不进分类统计与预算**。
  - `child`（子笔）：`parent_id` 指向父笔，各自有分类；**进分类统计与预算，不进余额**。
  - **落地状态与口径实现（重要）**：`DEFAULT 'normal'` + `parent_id NULL` 使存量行自然落入正确语义，`ALTER TABLE ... ADD COLUMN` 为纯追加零改写（§9.1 步骤 ③）。**口径已按共享常量实现**：`domain/entities/ledger_entry.dart` 的 `countsInOutflow`（父笔/普通计一次、**子笔不计**）、`countsInCategoryStats`（子笔/普通计、**父笔不计**）、`affectsBalance`（**子笔不计**）三个派生 getter 是唯一判定入口；SQL 侧 `account_repository.dart` 用 `split_role <> 'child'`、`budget_repository.dart` 用 `split_role <> 'parent'`，与三个 getter 同源，**没有两处各写一遍**（对应 PRD G-2.0）。
  - **分割交易的用例已落地**：`domain/usecases/split_usecases.dart`（父笔置空分类、`split_role='parent'`）。
- **`reimburse_status`：`[已落列]`（v4 迁移）。** `TEXT NOT NULL DEFAULT 'none'`，取值 `none` / `pending` / `reimbursed`；`DEFAULT 'none'` 即「未报销」，存量行语义天然正确。**注意**：报销单实体表 `reimburse_sheets` 仍未建（§10.1），该列是**单边预留**——列已在，表未在。
- **`reconciled_at`：`[已落列]`（v11 迁移，STORY-2.3 对账模式逐笔勾选）。** `INTEGER NULL`，存勾选时刻（UTC 毫秒）；NULL = 未勾选。选 **`reconciled_at` 时刻列而非布尔勾选列**，是因为对账是**月度重复动作**——布尔位在下次对账时无法区分「本月已勾」与「上月已勾」，时刻列天然携带周期信息。
- **贷款还本的收支口径（PRD STORY-10.2）不需要新字段**：每期还款生成**两笔**普通账单——利息笔 `source = 'recurring'`（周期引擎 `loan_repayment` 类型）、`type = 'expense'` 且计入收支；本金笔同 `source`、但 `type = 'transfer'`（负债账户 → 还款账户的位移），天然落入「transfer 不计入收支」的既有规则（§7.3），无需新增枚举。**用 `type='transfer'` 表达本金、而非加布尔列**，是因为「本金归还是资产负债位移」与「转账是资产负债位移」在建模上同构，复用同一条口径可以少一个需要跨页同步的判定位。
- **转账的「双账户符号翻转」不需要新字段**：`account_id`（转出）/ `to_account_id`（转入）已足够。账户维度查询时按 `account_id = ?` 取负、按 `to_account_id = ?` 取正（见 §7.1 的查询形态），**「入账方向」是查询期的派生量，不落列**（PRD G-2.1「两账户合计为 0」由此自然成立）。**代码已按此实现**：`AccountRepositoryImpl.balanceOf` 为五段式 `期初 − Σexpense + Σincome − ΣtransferOut + ΣtransferIn`。
- 备注的联想规则（STORY-1.3 AC4）不加索引、不做缓存：规则本身是「查最近 N 条同类备注」，量级小，索引收益低于维护成本。V3.0 若需要，走 FTS5（《04》§5.4 已列为验证项）。**代码实况**：联想由 `domain/services/category_suggester.dart` 以规则式（备注关键词 → 分类）实现，非 AI、非模糊检索。

**说明**

- **层级上限 2 是领域层约束，不是 DDL 约束**——`CHECK` 无法跨行判断「父节点是否为一级」。落地方式：领域服务（`category_repository.moveToParent` 已实现 kind 校验与「root 不可移动」判定）+ 一条数据校验测试（扫描全表，断言不存在三级链）。**这是有意的取舍**：用触发器保完整性会让每次写入多一层不可测的逻辑，代价大于收益。
- `icon_ref` 存**标识**而非路径：图标是包体最大变量（《04》§12），将来从字体子集切换为矢量绘制时，标识不变、实现变，数据零迁移。**代码实况：分类取色已全面以 `icon_ref` 为键**——`app/theme/theme_registry.dart` 的 `categoryColorMap` 使用 `food` / `shopping` / `transport` 等稳定 key，不再按中文一级分类名硬编码（《12》§8.1 的 `name`→`key` 迁移**已完成**，改名不会导致取色静默回退）。
- `note` 是**分类的边界说明**，与账单备注**同名不同物**——账单备注在 `transactions.note`，分类备注在 `categories.note`。代码里不得共用一个字段或一个 UI 组件。备注选填、≤ 30 字，**不参与搜索/筛选/统计，故不加索引**（与 `transactions.note` 同理）；但它是权威数据，随 `categories` 一起进备份与 V2.0 同步，**不能比照主题外观那种设备偏好做排除**（PRD STORY-1.3 AC9）。**代码已按此实现**：`note TEXT NULL` 经 v3 迁移落列（§9.1），`Category.withNote()` 专用写入方法，预置 63 处 `note:` 赋值。
- **备注可被清空**，所以 `insert`/`update` 的列清单必须显式包含 `note`（哪怕是 NULL）。注意 Dart 侧 `copyWith` 惯用的 `x ?? this.x` 语义会把「传 null」误读为「未传」——代码用专用 `withNote()` 规避，而非 `??` 兜底。见《编码指令-分类备注与分类体系》的陷阱清单。
- **`is_rigid`（刚性支出标记）：`[已落列]`（v10 迁移，PRD STORY-3.3）。** 代码实况：`_ddlCategories` 含 `is_rigid INTEGER NOT NULL DEFAULT 0`，`_migrate()` 有对应步（§9.1 步骤 ⑨）。取值 `0`/`1`；「仅一级分类可置 1」是**领域层约束**（同层级上限 2，不进 DDL）。它是权威数据，进备份与同步；**不参与分类统计口径**——只被「安全可花」的刚性支出预留读取，与 G-2 的收支判定正交，**不得混进任何收支/分类过滤条件**。`DEFAULT 0` 使存量分类自然落入「非刚性」，纯追加零改写。
- 分类合并不留痕（STORY-1.3 AC2）：事务内批量更新 `transactions.category_id` + 软删除源分类，**每条被改的账单各写一条 change_log**（否则 V2.0 同步无法传播这次合并）。**代码实况**：`category_repository.deleteAndReassign` 已实现该路径。
- `sort_order` 用整数步长（默认 10、20、30…），插入时取中值，避免每次拖动都重排全表。

```sql

```

**说明**

- **没有 `balance_cents` 列。** 所有账户的余额在**当前代码中都是派生值**，理由与实现见 §7.2。**代码实况**：`account_repository.dart::balanceOf` 对**全部账户类型**统一走五段式（`期初 − Σexpense + Σincome − ΣtransferOut + ΣtransferIn`，过滤 `split_role <> 'child'`），`type` 字段不改变余额算法。
- 信用卡属性组（`credit_limit_cents` / `credit_debt_cents` / `bill_day` / `due_day`）**已于 v10 落列**（见 §5.3 DDL 与 §9.1 v10），并已实现读写：

  > **设计意图：信用卡欠款余额是存储值（可写），不是派生量（PRD STORY-2.2）。** 这与 §7.2 的「余额不落列」**不矛盾**——§7.2 针对的是**非信用卡账户**（现金/储蓄卡/投资），它们不存在「对账直接写值」的需求，因此派生最安全。而信用卡的对账要求「录入银行 App 显示的欠款 → 直接修正余额」（PRD STORY-2.2 规则 2），若欠款余额是「Σ 账单」的派生量，这次修正会被下一次聚合覆盖，形成循环。因此信用卡欠款余额**必须落列**。
  >
  > **落地方案（已实现）**：`credit_debt_cents INTEGER NOT NULL DEFAULT 0` 承载欠款余额存储值（仅 `type='credit'` 有意义）。`CreditCardService`（`domain/services/credit_card_service.dart`）提供 `billDateForPurchase` / `dueDateForBill` / `interestFreeDays` / `amountDue` / `availableLimit` / `aggregatedDebtCents` / `aggregateDiff`；`CreditReconcileService` 在写欠款余额的同时**生成一笔 `source='reconcile'` 的凭证账单**（保证可追溯，且按 G-2 不计入收支）。聚合仅用于**对账页的校验提示**（`aggregateDiff`：「按账单聚合 X，与当前余额 Y 相差 Z」），不参与余额的最终取值。
  >
  > **当前实现与设计的差异（必须记录）**：`_ddlAccounts` 中落的是 **`credit_debt_cents`**（非设计早期的 `credit_balance_cents` 命名），且 `AccountRepositoryImpl.balanceOf` **仍对全部账户类型统一走五段式派生**——即落列已就绪、但余额算法的 `type` 分流尚未启用。`credit_card_service.dart` 的聚合/对账路径已读写该列，说明存储值语义**已落地**；V2.0 若要实现「余额取值也按 `type` 分流」，属余下的算法层接线，不是加列。
  >
  > **为什么不违反 §7.2 的三条理由**：① 它是**唯一权威可写量**，同步时作为普通字段参与合并，不会出现「两端各自增量维护同一个派生值」的漂移（漂移的根源是「派生」，存储值不存在这个问题）；② 「漏更新就永久错误」的风险由「账单入账路径唯一入口是 Repository」+ 对账校验共同兜住；③ 它是**单值修正**语义，不是高频增量维护。**关键区别在语义**：非信用卡余额是「账单的函数」，信用卡欠款余额是「一个独立事实，账单只是它的增量」。

- 账户类型选择器中 V2.0 的类型（`loan_out` / `loan_in`）在 V1.0 置灰，**这是 UI 行为，数据层不受限**——枚举值已定义，测试数据可以直接建全类型账户。**代码实况**：`accounts_page.dart` 的类型选择器已开放**现金 / 储蓄卡 / 信用卡 / 投资**四项。

### 5.4 `change_log` 变更日志（设备本地，V2.0 同步的唯一输入）

```sql
CREATE TABLE change_log (               -- 代码实况：data/db/database.dart `_ddlChangeLogs`
  local_revision INTEGER PRIMARY KEY AUTOINCREMENT,  -- 本设备单调递增序号，兼同步游标
  entity_type    TEXT    NOT NULL,                   -- EntityType
  entity_id      TEXT    NOT NULL,
  op             TEXT    NOT NULL,                   -- ChangeOp
  device_id      TEXT    NOT NULL,
  base_revision  INTEGER NOT NULL DEFAULT 0,         -- 变更前实体版本
  payload        TEXT    NOT NULL,                   -- 变更前后值（JSON），见下
  payload_hash   TEXT    NOT NULL,                   -- 幂等去重与冲突检测辅助
  changed_at     INTEGER NOT NULL                    -- UTC 毫秒
);
```

**代码实况**：`data/sync/change_log_writer.dart` 已按上述形态写入——`payload = jsonEncode({'before': …, 'after': …})`，`payload_hash = sha256(payload)`，`entryPayload()` 覆盖 **18 个字段**。

**`entryPayload()` 的 18 个字段**（`change_log_writer.dart` 逐字，顺序即代码中的声明顺序）：

| # | 字段 | 说明 |
|---|---|---|
| 1–7 | `id` / `book_id` / `type` / `amount_cents` / `currency` / `category_id` / `account_id` | 账单主字段 |
| 8–13 | `to_account_id` / `occurred_at` / `note` / `source` / `batch_id` / `created_at` | 转账转入账户、业务时刻、备注、来源、周期批次、创建时刻 |
| 14–18 | `updated_at` / `deleted_at` / `revision` / `device_id` / `base_revision` | 审计字段块 |

> ⚠️ **`entryPayload()` 未覆盖的 4 列（本轮核验发现）**：`split_role` / `parent_id` / `reimburse_status` / `reconciled_at` 虽已于 v4/v11 落列，但**未进入 18 字段清单**。后果：一旦同步升级为 change_log 驱动的字段级合并（§10），这四列的变更**无法传播**（整库替换同步不受影响）。修法：把这四列加入 `entryPayload`，并保证各实体写入时字段集合稳定（见下方「字段集合」说明）。登记见 §11 C22 与 §12 未决项。

> **`currency` 的写入细节**：`entryPayload` 签名把 `currency` 声明为 `required`，而 `_payload()` 传入的是 `e.currency`——`LedgerEntry.currency` 在构造时已由 `_fromRow` 兜底为 `'CNY'`（`(row['currency'] as String?) ?? 'CNY'`），因此不会写入 `null`。
>
> **类别实体的 payload 更短，且不统一**（这是有意的，不是疏漏）：`AccountRepositoryImpl._payload` 只含 6 个字段（`id` / `name` / `type` / `opening_balance_cents` / `sort_order` / `is_hidden`），`CategoryRepositoryImpl._payload` 含 9 个字段，`Budget` / `RecurringRule` 的 `_payload` 含全字段 + 审计块。因此 **§5.4 的「统一三段式」描述的是 `before` / `after` 的「结构」，不是「字段集合」**——字段集合由各实体自行决定，只要保证「同一实体的两次写入字段集合一致」即可（否则 3-way 合并会误判字段被删）。`ledger_repository` 的物理删除（`hardDelete` / `purgeExpired`）额外改用 `entryPayload()` 显式构造 `before`，与正常路径一致。

**`payload` 的形态**（统一三段式，不含未变更字段）：

```jsonc
// insert：before 为空，after 为全字段
{"before": {}, "after": {"id": "01J...", "amount_cents": 2500, "category_id": "01J...", "occurred_at": 1759123456789, "...": "..."}}

// update：仅含被修改字段的前后值
{"before": {"amount_cents": 2500, "note": "午饭"}, "after": {"amount_cents": 3200, "note": "午饭（AA）"}}

// delete：after 为空，before 为全字段
{"before": {"id": "01J...", "amount_cents": 2500, "...": "..."}, "after": {}}
```

**为什么 `payload` 必须在 V1.0 落地**（对《04》§6.1 的补充）：

《04》§6.3 要求「字段级三方合并，`base_revision` 定位共同祖先，逐字段比对」。**但业务表只保留最新值——祖先的内容在覆盖时就丢失了。** 没有 `payload`，V2.0 只能退化为「整行取最后写入」，PRD 的「字段级自动合并 + 自动解决率 ≥95%」随之失效。而这件事**无法事后回填**：V1.0 期间发生的历史变更，其前后值在没有记录的情况下不可能重建。这正是 §2 判据里「后补需要触碰历史行」的典型，必须在 V1.0 落地。

**顺带收益**：V3.0 的操作日志（F7.8，90 天）需要的正是同一份数据，届时只是换个查询视图，不必再建一套审计体系。

**两处对《04》§6.1 的修正**：

| 项 | 《04》原表述 | 本文档 | 理由 |
|---|---|---|---|
| `local_revision` 的来源 | 由 `app_meta` 维护单调计数器 | `INTEGER PRIMARY KEY AUTOINCREMENT` | 独立计数器在并发写事务下需要额外保证，而 SQLite 的 `AUTOINCREMENT` 在事务内天然单调且永不重用（回滚也不消耗）。**少一个可能与实际数据不一致的状态** |
| `idx_change_seq ON change_log(local_revision)` | 列为索引 | **删除**，`local_revision` 即主键（rowid），前缀查询天然高效 | 冗余索引只增加写代价 |

**关于「金额入 change_log」不等于违反隐私红线**：数据库是设备本地、整库加密的数据（PRD STORY-4.2），包含金额是它的本职；《06》A1/A3 的隐私红线针对的是**日志与诊断包**这类会离开设备的产物。两者必须在实现上物理隔离——`change_log` 只有同步通道能读，日志门面拿不到它。

### 5.6 `daily_stats` 统计聚合（派生，可全量重建）

```sql
CREATE TABLE daily_stats (
  book_id       TEXT    NOT NULL,
  day_key       TEXT    NOT NULL,                  -- 'YYYY-MM-DD'，本地记账日
  category_id   TEXT    NOT NULL,                  -- '' 表示「未分类」
  account_id    TEXT    NOT NULL,                  -- '' 表示「无账户」
  expense_cents INTEGER NOT NULL DEFAULT 0,
  income_cents  INTEGER NOT NULL DEFAULT 0,
  tx_count      INTEGER NOT NULL DEFAULT 0,
  updated_at    INTEGER NOT NULL,
  PRIMARY KEY (book_id, day_key, category_id, account_id)
);
```

**说明**

- **只统计 `type` 为 `expense` / `income` 的账单。** 转账与借贷类是账户间的位移，计入会同时虚增支出与收入——这是记账产品最容易出错的口径之一（见 §7.3）。
- 记账月边界（月起始日 1–28 号，PRD STORY-5.1）**不落库**，在查询期由 `day_key` 的区间表达。
- 主键已覆盖 `(book_id, day_key)` 前缀查询，**无需额外索引**。
- `''` 作为「未分类 / 无账户」的哨兵值而非 `NULL`：SQLite 的主键列允许 `NULL` 且**不保证唯一**（`NULL != NULL`），用 `NULL` 会造成同一组合出现多行。这是一个容易踩的坑。**代码已按此实现**（`ledger_repository.dart` 的 `_upsertDailyStats` 用 `accountId ?? ''` 兜底）。
- **`account_id` 是「写而不读」的预留维度**：写入侧严格按四列复合键 upsert（每行都带真实 `account_id`），但**读取侧目前不使用它**——`LedgerRepositoryImpl.monthSummary` 是 `GROUP BY category_id`，报表与预算都只看分类维度，跨账户额合并。保留该维度的理由是为 V2.0 的「按账户看消费构成」预留，**代价是行数放大**（同一 `day_key + category_id` 会按账户拆成多行）。重建 `daily_stats` 时**必须按同样四列分组**，否则行集合与写入侧不一致（见 §8）。
- **`deleted_at` 不在本表**：派生表不需要软删除语义——它是可丢弃可重建的，删除即物理 `DELETE`（重建路径的唯一写法）。这与三张权威表带 `deleted_at` 形成对比，是本节性质分类的直接体现。

## 6. 索引与约束（汇总）

```sql
-- 流水页 keyset 分页（游标 = (occurred_at, id) DESC）
CREATE INDEX idx_entry_book_time  ON transactions(book_id, occurred_at DESC, id DESC) WHERE deleted_at IS NULL;
-- 分类下钻、分类合并、报表按分类聚合
CREATE INDEX idx_entry_category   ON transactions(category_id, occurred_at DESC)      WHERE deleted_at IS NULL;
-- 账户余额聚合、账户删除前的引用检查
CREATE INDEX idx_entry_account    ON transactions(account_id, occurred_at DESC)       WHERE deleted_at IS NULL;
CREATE INDEX idx_entry_to_account ON transactions(to_account_id, occurred_at DESC)    WHERE to_account_id IS NOT NULL AND deleted_at IS NULL;

-- 周期生成批次：整批撤销（按 batch_id 归集一次生成的多笔）
CREATE INDEX idx_entry_batch      ON transactions(batch_id)                            WHERE batch_id IS NOT NULL;

-- 分割交易父笔展开（v4 落 parent_id 后建）
CREATE INDEX idx_entry_parent     ON transactions(parent_id, occurred_at DESC)         WHERE parent_id IS NOT NULL AND deleted_at IS NULL;

-- 分类：同级不重名
CREATE UNIQUE INDEX uq_category_name ON categories(COALESCE(parent_id, ''), name) WHERE deleted_at IS NULL;
CREATE INDEX idx_category_parent ON categories(parent_id, sort_order) WHERE deleted_at IS NULL;

-- 账户：不重名
CREATE UNIQUE INDEX uq_account_name ON accounts(name) WHERE deleted_at IS NULL;
CREATE INDEX idx_account_sort ON accounts(sort_order) WHERE deleted_at IS NULL;

-- 变更日志：按实体追溯历史（V3.0 操作日志 / V2.0 祖先重建）
CREATE INDEX idx_change_entity ON change_log(entity_type, entity_id, local_revision);

-- budgets：总预算唯一 / 分类预算唯一 / 按账本列表（表与索引均已实现）
CREATE UNIQUE INDEX uq_budget_total    ON budgets(book_id)             WHERE scope = 'total'    AND deleted_at IS NULL;
CREATE UNIQUE INDEX uq_budget_category ON budgets(book_id, category_id) WHERE scope = 'category' AND deleted_at IS NULL;
CREATE INDEX        idx_budget_book    ON budgets(book_id)             WHERE deleted_at IS NULL;

-- recurring_rules：调度器取「到期待执行」规则 / 按账本列表（表与索引均已实现）
CREATE INDEX idx_recurring_due  ON recurring_rules(next_run_at) WHERE is_enabled = 1 AND deleted_at IS NULL;
CREATE INDEX idx_recurring_book ON recurring_rules(book_id)     WHERE deleted_at IS NULL;

-- rules：按账本取启用规则、优先级倒序（表与索引均已实现）
CREATE INDEX idx_rule_book ON rules(book_id, priority DESC) WHERE deleted_at IS NULL AND is_enabled = 1;

-- daily_stats：主键 (book_id, day_key, ...) 已覆盖按日/按月的区间查询，无需额外索引
```

> **本节索引与 `database.dart` 的 `_indexes` 清单（17 项）逐字对应。** 上一版本文档在此处有三处索引名与代码不符、一处过滤条件不符，已按代码校正（差异记录见 §11 的 C12）；索引数已由 15 项校正为 17 项（补 `idx_entry_parent`、`idx_rule_book`）。

**要点**

- **全部使用部分索引（`WHERE deleted_at IS NULL`）**：软删除是常态语义，把「存活」写进索引定义，查询侧就不必带过滤条件，索引体积也小。
  - **唯一的例外是 `idx_entry_batch`**：它只声明 `WHERE batch_id IS NOT NULL`，**不带 `deleted_at IS NULL`**。这是代码实况，且是有道理的——该索引服务的是「按批次查全部行」（含已删除，用于撤销后追溯），过滤 deleted_at 反而会让查询退化为全表扫描。
- **keyset 分页，禁用 OFFSET**（《04》§5.4）：`idx_entry_book_time` 的列顺序即游标顺序。
- **唯一索引只约束存活行**：删除「咖啡」后再新建「咖啡」不冲突。这一点配合 §7.5 的软删除策略才能成立。
- **`budgets` 的两个唯一索引是业务规则的唯一执法者**：「每账本至多一个总预算」与「每账本每分类至多一个预算」都不在领域层做全表检查（会有竞态），而是交给 partial unique index（§5.7）。
- **不使用数据库级外键约束**（见 §7.6）。
- **`idx_entry_parent` 已存在**：服务分割交易的父笔展开（`transactions.parent_id` 已于 v4 落列，见 §5.1）；定义为 `ON transactions(parent_id, occurred_at DESC) WHERE parent_id IS NOT NULL AND deleted_at IS NULL`。
- **17 项索引的实际构成**：`transactions` 6（含 `idx_entry_parent`）+ `categories` 2 + `accounts` 2 + `change_log` 1 + `budgets` 3 + `recurring_rules` 2 + `rules` 1（`idx_rule_book`）= 17。`daily_stats` 0（主键已覆盖）。

### 6.1 连接层 PRAGMA（`database.dart` 实况）

索引之外，连接层的四行 PRAGMA 同样影响数据正确性与性能，代码在 `_open()` 中逐条设置：

```dart
_db.execute('PRAGMA journal_mode = WAL');    // 读写并发：报表查询不阻塞记账写入
_db.execute('PRAGMA foreign_keys = ON');     // 见 §7.6：无 REFERENCES 声明，故无实际约束
_db.execute('PRAGMA busy_timeout = 5000');   // 锁等待 5s，避免多连接瞬时冲突即失败
// WAL + NORMAL 是移动端 durability / throughput 的标准取舍
```

> **`synchronous` 未显式设置**，代码注释说明取 WAL + 默认 `NORMAL`：断电最多丢失最近若干事务（不损坏数据库），换日常写入吞吐。对记账产品这是合理取舍——单笔记账丢失可由用户重录，而 `FULL` 会让每次落库都 fsync，直接冲击「落库 ≤ 200ms」的指标（《01》§八）。

## 7. 关键建模决策

### 7.1 转账用「单行双向」，不用「双行」

**决策**：一笔转账 = `transactions` 中的**一行**，`account_id` 为转出、`to_account_id` 为转入。

| 方案 | 评价 |
|---|---|
| 单行双向（采纳） | 转账是原子操作，单行天然原子：一条 change_log、一个 revision、一次事务。3-way 合并时要么整笔合并、要么整笔冲突，不会出现「转出成功、转入丢失」 |
| 双行互链 | 两行 = 两条 change_log、两个 revision。V2.0 多端合并下**可能只合并到一半**，产生金额不平的转账——这类不一致在记账产品里是最难向用户解释的缺陷 |

代价：查询账户流水时需要 `account_id = ? OR to_account_id = ?`，因此为 `to_account_id` 单独建索引（§6）。这个代价远小于数据不一致的代价。

### 7.2 余额不落列：派生值不进权威表

**决策**：`accounts` 表只存 `opening_balance_cents`（期初余额），**不存当前余额**。余额 = 期初 + Σ(该账户所有未删除、且「计入账户余额」的账单的带符号金额)，走索引 `idx_entry_account` 聚合。

**适用边界（设计意图）**：本条**只适用于非信用卡账户**（`cash` / `debit` / `investment`）。**信用卡账户在设计上是唯一例外**——其「欠款余额」是**存储值（可写）**，理由见 §5.3 的信用卡说明框（对账需直接写值，不能是聚合派生）。

> ⚠️ **当前实现与设计的差异**：信用卡存储值**列已落地**（v10 追加 `credit_debt_cents`，见 §5.3），`credit_card_service.dart` 已实现读写；但 `account_repository.dart` 的 `balanceOf` **仍对全部账户类型统一走** `期初 − Σexpense + Σincome − ΣtransferOut + ΣtransferIn`。因此**当前所有账户（含信用卡）的余额取值都走派生**——余下工作是把 `balanceOf` 按 `type` 分流（算法层接线，非加列）。

否决「物化余额列」的三条理由（针对非信用卡账户）：

1. **它是派生值，不该进入同步范围。** V2.0 两端各自增量维护余额，字段级合并会把两个派生值当作独立字段比对，产生大量无意义冲突；冲突解决后两端余额还可能不一致。**同步的只有权威数据，派生值由各端自行重算。**
2. **任何一条漏更新余额的写入路径，都会造成永久性错误**，且错误不报错、只体现为显示不对。相比之下，聚合查询最坏只是慢。
3. **V1.0 的量级不需要它**：账户数是 2–5 个，PRD 对资产页没有耗时指标（「万条账单 60fps」针对的是流水列表）。`idx_entry_account` 上的聚合是索引扫描，万条量级为毫秒级。

**为何信用卡例外不违反上述逻辑**：信用卡欠款余额**不是「账单的函数」**，而是一个**独立事实**——银行账单上的欠款额是用户实际欠银行的钱，账单记录只是它的增量维护手段。对账时用户录入的是这个**事实值**，因此它必须可写。它作为存储值参与同步时是普通字段，不存在「两端各自维护派生值」的漂移问题。**判断标准是语义：派生量 = 可被完全重算的从属值；存储值 = 被独立记录、无法由其他字段完全推出的权威事实。**

**触发条件**：若实测出现性能问题，加一张 `account_balance_cache` 派生缓存表（纯追加、可重建、不参与同步），而不是往权威表加列。这个区分很重要——缓存在权威表里，就再也拿不出来了。

### 7.3 统计按「日」粒度，而非按月

**决策**：派生物化表按**本地记账日**聚合（`daily_stats`），月/季/年统计全部由查询期的 `day_key` 区间聚合得出。

这不是网格上的美化，它同时解决三件事：

1. **覆盖了 PRD 的一处需求缺口。**《04》§5.5 的按月聚合表**无法产出**报表页的「月收支结余走势（按日折线/柱）」（STORY-3.1 图表①）——那张图需要日粒度。按日聚合是唯一同时满足折线图与月度统计的粒度。
2. **取消了 PRD 里的一个「重度操作」。** PRD STORY-5.1 AC2 原规定：月起始日变更时「全部月度数据按新边界重算」，并要求提示用户「将重新计算所有月度统计」。**在日粒度下，月起始日只影响查询期的日区间起点，统计数据一行都不用重算**——切换是瞬时的，提示文案随之取消。✅ **已回写 PRD STORY-5.1 AC2–AC4 与《01》F3.1**（行为变更已落地到文档）。
3. **口径唯一。** 「这笔账单属于哪个月」在全产品只有一个计算入口（`AccountingCalendar`，配合《06》D6 与《05》B2 的 Clock 注入），不再有「聚合表按一套口径、报表按另一套」的可能。

**取舍说明（必须写明）**：`day_key` 是**写入时的本地日**，跨时区旅行不会自动改写历史行。若用户需要按新时区重算，做法是重建 `daily_stats`（§8），而不是改权威数据——这正是把统计做成「派生表」的价值：**它可以随时被扔掉重算，权威数据不行。**

### 7.5 软删除 + 30 天 GC：V2.0 回收站因此近乎免费

**决策**：用户点删除时，**UI 层是「不可恢复」的物理删除语义，数据层写软删除**（`deleted_at` + `change_log(op = delete)`）；软删除行与 change_log 共用同一个 30 天 GC 任务物理清除。

三条理由：

1. **同步必须能传播删除。** V2.0 若用物理删除，其他设备无法得知这条账单「被删了」还是「从未见过」——这是同步里最经典的坑。软删除 + change_log 的 `delete` 记录是唯一正解。
2. **V2.0 回收站（F7.7，30 天）因此变成一个纯前端功能**：加一个「已删除」列表 + 恢复操作即可，**零数据迁移**。注意 GC 窗口（30 天）与回收站保留期（30 天）本就一致，不需要两套逻辑。
3. **对 V1.0 用户的体验承诺仍然成立**：V1.0 UI 层没有恢复入口，用户确实无法恢复；30 天后数据被物理清除，「不可恢复」在物理意义上也为真。**因此 PRD 的删除确认文案「删除后不可恢复」无需修改。**

**代码实况：数据层已经全部就绪，缺的只是 UI 入口。** `LedgerRepositoryImpl` 已实现回收站所需的**全套四个方法**（这段原写「V1.0 没有恢复入口」，指的是 UI 层，措辞已精确化）：

| 方法 | 职责 | 关键实现 |
|---|---|---|
| `listDeleted({bookId, limit})` | 列已删除账单 | `WHERE deleted_at IS NOT NULL ORDER BY deleted_at DESC` |
| `restore(id)` | 恢复 | 校验 `deletedAt != null`（否则 `entry.not_deleted`）→ `copyWith(clearDeletedAt: true)` + `revision + 1` + 回加 `daily_stats` + 写 `update` 的 change_log |
| `hardDelete(id)` | 物理删除单条 | 仅允许删已软删除的行；**删除后仍写一条 `delete` 的 change_log**（否则对端永远不知道这行没了） |
| `purgeExpired({before})` | 30 天 GC 批处理 | 先 `SELECT` 捞出将删行 → `DELETE` → **逐行补写 change_log**，全程单事务 |

> **由此得出两条设计确认**：① 恢复路径**必须回加 `daily_stats`**（`restore` 调用 `_upsertDailyStats(restored, isIncrement: true)`），否则恢复后统计少一笔；② 物理删除路径**仍必须写 change_log**——这一点容易漏，因为「行已经没了」直觉上不需要再通知谁，但 V2.0 增量同步正是靠这条记录去对端执行删除。`hardDelete` 与 `purgeExpired` 都正确处理了。
>
> **实现状态**：`features/settings/trash_page.dart`（回收站页）**已存在并全链路落地**（列表 / 恢复 / 彻底删除 / 清空，配套 `trash_test`）。数据层四项（`listDeleted` / `restore` / `hardDelete` / `purgeExpired`）本就齐备，V2.0 回收站功能可直接启用，无需补 UI。

### 7.6 不使用数据库级外键约束

**决策**：`category_id` / `account_id` / `to_account_id`（以及 V2.0 的 `parent_id`）均**不声明 `REFERENCES`**，完整性由领域层 + 一条可执行的孤儿检查承担（PRD STORY-1.3 AC2 要求的「校验分类表无 dangling 引用」正是这条检查）。

理由：**外键在同步场景下会变成故障源。** V2.0 应用远端变更时可能出现「账单先到、分类后到」的乱序，此刻插入外键会直接失败，而正确做法是暂存/容忍短暂悬空、待依赖到齐后再校验。软删除又叠加了「引用指向已软删除的行」这一合法状态。把完整性判断交给领域层与批处理校验，比交给数据库在同步场景下更可控。

**这必须现在决定**：SQLite 无法 `ALTER TABLE ... ADD CONSTRAINT`，后补外键 = 重建全表。

> **代码实况**：数据库连接**确实开启了** `PRAGMA foreign_keys = ON`，但**列上一律没有 `REFERENCES` 声明**，因此不构成任何实际外键约束——与本节决策一致。开启该 PRAGMA 是无害的（没有约束可执行），但不要因此误认为存在数据库级引用完整性。
>
> **连接层其余 PRAGMA**（`_open()` 实况，全文见 §6.1）：`journal_mode = WAL`（读写并发，报表查询不阻塞记账写入）、`busy_timeout = 5000`（锁等待 5s）。`synchronous` 未显式设置，取 WAL 下的默认 `NORMAL`。
>
> **⚠️ 一处与本节决策相抵触的现有实现**：`AccountRepositoryImpl.softDelete` 用一条 `SELECT COUNT(*) ... WHERE (account_id = ? OR to_account_id = ?) AND deleted_at IS NULL` 做「有账单就不许删账户」的前置检查（PRD STORY-2.1 AC2），违反时返回 `ConflictFailure('account.has_transactions')`。**这是领域层检查，不是数据库约束**——与本节决策一致，属于「完整性由领域层承担」的正面例子，记录在此以免被误读为外键。

### 7.7 枚举不加 CHECK 约束，但预留 `unknown`

**决策**：枚举列只存 `TEXT`，不加 `CHECK (type IN (...))`。

理由：**改 CHECK 约束在 SQLite 里需要重建表并重写全表数据**——而枚举值恰恰是最会变的东西（V2.0 加 `import`，V3.0 加 `ocr` / `ai`，V4.0 可能加更多）。给一个必然会变的集合加上一个「变就要重写历史行」的约束，与 §2 的判据直接冲突。

**完整性由两层保证**：写入侧用 Dart 枚举 + 序列化转换层（编译期穷尽，配合《05》的 `exhaustive` 系列规则）；读取侧遇未知值降级为 `unknown` 并记日志，**不抛异常**（§4.4）。

### 7.8 数据库只约束「永不变的不变量」

**决策**：全库只保留一条业务 `CHECK`：`amount_cents > 0`（`transactions` 与 `budgets` 两表各有一条，字面相同）。金额上限、层级上限 2、分类名长度——这些是**产品策略**，放领域层校验 + 集中常量（《05》C3），不进 DDL。

分界线很清楚：`amount_cents > 0` 来自「方向由 type 表达」的建模选择，它与表结构共生，除非重塑模型否则不会变；而「上限是多少」是一个产品决策，明天就可能因为支持企业记账而调整——让它进入需要重建表才能修改的约束里，是自找麻烦。

**上限常量的代码实况（换算已核正）**：`core/money/money.dart` 定义 `static const int maxCents = 9999999999;`，即 **9,999,999,999 分 = 99,999,999.99 元**。判定入口是 `Money.withinProductLimit`（`cents.abs() <= maxCents`），另有 `clampToLimit()` 做夹取。**V1.0 的输入控件与 `BudgetRepositoryImpl` / `RecurringRepositoryImpl` 的写入校验都引用这一常量**，因此改上限只改一处。

> **注意**：金额上限**不进 DDL 是正确的**（本节决策），但「PRD 与代码的数值必须一致」是另一件事。以代码为准：**99,999,999.99 元**（`maxCents = 9999999999`，单位是分）。本文档上一版曾误换算为 `999,999,999.99` 元（把分当成了元×10 的关系），已核正；PRD 与《01》中的 `99,999,999.99` 与代码一致，无需改动。

## 8. 派生表的一致性、巡检与重建

`daily_stats` 是唯一派生表，它的正确性完全依赖「与账单写入同事务维护」+「异常时可重建」。三层机制：

| 机制 | 做法 |
|---|---|
| 写入期 | 与账单插入/更新/删除**在同一个事务内** upsert 受影响的行（含新旧两行——更新时要回退旧值、加上新值） |
| 巡检期 | **每次冷启动做一次低成本比对**：`SELECT COUNT(*) FROM transactions WHERE deleted_at IS NULL` 与 `daily_stats.tx_count` 的合计比对，不一致即触发重建，并把 `stats.checksum` 写入 `app_meta` |
| 重建 | 单事务内 `DELETE FROM daily_stats` 后由 `transactions` 全量重算。触发时机：迁移 `finalize`、巡检不一致、数据导入后（V2.0）、用户手动「重算统计」（设置页的隐藏入口，也是客服兜底手段） |

**跨时区语义的默认策略**是重建，不是改写：`day_key` 冻结于写入时刻，重建会按**当前设备时区**重新计算。这条写进领域层注释（《05》C4）。

**为什么必须可重建**：只要派生表可以随时被丢弃重算，任何一致性 bug 的最坏后果就只是「显示不对，重启一次即恢复」，而不会变成「数据丢了」。这是把统计做成派生表而不是往权威表塞计数列的第二个价值。

**✅ 三层机制均已实现（2026-10-15 代码复核实况）**：

- **「写入期」已实现且实现得正确**：`LedgerRepositoryImpl` 的 `create` / `update` / `softDelete` 全在 `_db.transaction(() {...})` 内，`update` 与 `softDelete` 都**成对调用** `_upsertDailyStats(old, isIncrement: false)` 与 `_upsertDailyStats(entry, isIncrement: true)`（软删除只调前者），回退旧值 / 加上新值的语义完备；门禁为 `entry.countsInCategoryStats`（见 §7.3）。
- **「巡检期」已实现**：`ledger_repository.dart::verifyDailyStats()` 用 `SELECT COUNT(*) FROM transactions WHERE deleted_at IS NULL AND type IN ('expense','income') AND source <> 'reconcile'` 与 `SELECT COALESCE(SUM(tx_count),0) FROM daily_stats` 比对；`bootstrap.dart::runDailyStatsIntegrityCheck` 在每次冷启动调用，`main.dart` L74 以 `unawaited(...)` 接线。
- **「重建」已实现**：`ledger_repository.dart::rebuildDailyStats()` 在单事务内 `DELETE FROM daily_stats` 后由 `transactions` 全量重算（`_upsertDailyStats(entry, isIncrement: true)`），并写入 `app_meta` 的 **`stats.built_at` / `stats.checksum`**（`ON CONFLICT ... DO UPDATE`）。`change_log` 的 GC `runChangeLogGc` 亦于 `main.dart` L75 接线。

> ⚠️ **残余不一致（见 §7.3 的说明框）**：`verifyDailyStats` / `rebuildDailyStats` 两条 SQL 未排除 `split_role='parent'`，存在潜伏的双算 / 巡检误报，修法已在 §7.3 给出。
>
> **重建函数的最小编号提醒**：`daily_stats` 的主键含 `account_id`（四列复合），重算按四列 `GROUP BY`；但**读取侧当前不使用 `account_id` 维度**——`LedgerRepositoryImpl.monthSummary` 只按 `category_id` 分组，跨账户额合并。因此 `account_id` 目前是「写而不读」的预留维度，重算时不可省略，否则写入侧与重算侧的行集合会不一致。

## 9. 迁移策略

| 项 | 规定 |
|---|---|
| 版本号 | SQLite `user_version`（代码常量 `kSchemaVersion`，见 `data/db/database.dart`），从 1 起。**已发布的号冻结：只能追加新号，不得复用或回退**。**代码实况 `kSchemaVersion = 11`**，已占用的号：v1 初始建表（11 张表）、v2 `transactions.batch_id`、v3 `categories.note`、v4 `transactions.split_role/parent_id/reimburse_status`、v5 `rules` 表（`_init` 建，无 ALTER）、v7 `savings_goals.goal_type/remaining_terms`、v10 `accounts` 信用卡四列 + `categories.is_rigid`、v11 `transactions.reconciled_at`（完整清单见 §9.1） |
| 粒度 | 每个发布版本对应一个 `MigrationStep`；**禁止跨版本跳跃的隐式迁移**（升级路径按顺序逐步执行，每一步都可单测） |
| 允许的操作 | `CREATE TABLE` / `CREATE INDEX` / `ALTER TABLE ... ADD COLUMN`（必须带默认值） |
| 禁止的操作 | 改列类型、改主键、`DROP COLUMN`、重命名表或列。（`DROP COLUMN` 在 SQLite 3.35+ 语法上可用，但会重写全表且不可逆，一律禁止） |
| 事务 | 每步迁移在单独事务内完成；DDL 与数据变更同事务，失败整体回滚 |
| **迁移前备份** | **无条件**先生成一份一致性快照（`VACUUM INTO`），备份失败即中止升级并进入可诊断状态而非继续。这是《06》B4 的落点，也是 V1.0→后续所有版本的保命机制 |
| 回归验证 | 每个历史版本保留一份数据库快照夹具，CI 执行「装载旧快照 → 升级 → 校验」 |
| 校验内容 | ① 表结构与索引齐备；② 各表行数与预期一致；③ `daily_stats` 可被完整重建且与升级前口径一致；④ `change_log` 的 `local_revision` 连续无断层 |
| 备份文件兼容 | 备份头携带 `appVersion` + `schemaVersion`；恢复时若备份版本高于当前 App，拦截并提示升级（PRD STORY-4.1 AC2） |
| 数据重置的例外 | 卸载重装（PRD STORY-4.1 AC4）不在迁移范围内——本地数据随卸载清除，商店描述已注明「卸载前请先备份」 |

### 9.1 迁移步清单：v1 → v11（全部已提交）

**代码中实际存在 v1–v11 共 11 个版本号**，`_migrate()` 内的 `ALTER TABLE ... ADD COLUMN` 均为「允许的操作」（纯追加、零数据改写），新装路径由各 `_ddl*` 直接建成最新版（不走 ALTER）。

**v1 → v2（`transactions.batch_id`）**

```sql
ALTER TABLE transactions ADD COLUMN batch_id TEXT NULL;
```

**v2 → v3（`categories.note`）**

```sql
ALTER TABLE categories ADD COLUMN note TEXT NULL;
```

配套三点（两步共用）：

1. `_ddlTransactions` / `_ddlCategories`（`data/db/database.dart`）同步加列——新装直接建成最新版，不走 ALTER 路径。
2. `kSchemaVersion` 逐级升（1 → 2 → 3）。
3. `_migrate()` 用 `PRAGMA table_info(...)` 判列是否存在后再执行。**必须先判存在**：新装路径建表时已带上该列，无条件 ALTER 会报 duplicate column。

存量行的 `note` / `batch_id` 均为 NULL，即「未填」，语义正确，**不做回填**。

**v3 → v4 及其后（v4–v11，全部已提交）**

## 10. 与同步架构的衔接

**硬规则**（对应《04》§6.4，此处用表分类表述，更不易违反）：

1. **同步的唯一输入是 `change_log`。** 业务代码中不得出现任何「如果在线就上传」的分支。
2. **派生表永远不能作为同步来源。** `daily_stats` 不写 change_log、不上传。若把两端各自增量维护的聚合值同步出去，字段级合并会把它当作独立字段比对，产生大量无意义冲突——而且合并后的值仍是错的（它不对应任何一端的真实明细）。
3. **权威表以「实体 + revision」为单位合并**：`base_revision` 定位共同祖先，`payload` 提供祖先与双方的字段值（§5.4），逐字段比对；无共同祖先或同字段冲突时，两个版本都保留、进入「冲突中心」由用户裁决（PRD F7.2）。
4. **`device_id` 不随备份迁移**（§5.5）——这是多端识别 revision 归属的基础，两台设备共用同一个 ID 会让合并逻辑失去判断依据。
5. **前向兼容**：读到未知枚举值降级为 `unknown`、未知字段忽略，不抛异常。低版本 App 遇到高版本数据必须是「部分功能不可见」，而不是崩溃。

> ⚠️ **代码实况与上述规则的偏差（必须记录）**：当前 `data/sync/webdav_sync_service.dart` 实现的是**整库文件同步**——上传走 `VACUUM INTO` 生成一致性快照后传整个 `.sqlite` 文件，下载则替换本地 `plain.sqlite`。**它并不消费 `change_log`**，因此上述 1–3 条是 **V2.0 的目标架构**，而非当前实现。
>
> 这意味着两点：① `change_log` 的 `payload` / `base_revision` 仍是有价值的 V1.0 前置投入（§5.4 的理由不变），因为整库同步无法演进为字段级合并；② **同步从「整库替换」升级为「change_log 驱动的增量合并」，是一次架构替换而非增量开发**，需要在《04》§6 明确记录。整库替换方案在多端并发写入时会直接丢数据（后上传者覆盖先上传者），**不可用于 V2.0 的正式同步**。

**V2.0 需要新增但 V1.0 不建的表**（均属纯追加）：

- `conflict` 冲突副本表（PRD 的「两个版本都保留」需要一个落地位置）
- `sync_meta` 同步元数据（PRD §7 的「同步元数据」实体：设备 ID、同步位点、冲突副本引用）
- `books` 账本表（复用 `app_meta['book.default_id']`）

> 上述三表与整库同步→增量合并的**分阶段迁移路径（S1–S6）**见《04》§6.5。其中 S6 与本节的 GC 策略强耦合：**`change_log` 的 30 天 / 5 万行裁剪必须在确认所有已知设备已消费到更早位点后才能执行**，否则会永久丢失尚未同步的变更。
