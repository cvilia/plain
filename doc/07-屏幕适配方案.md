## 1. 结论先行

**不采用任何"整体等比缩放"方案。采用「断点 → 布局壳 → 约束驱动 → 机器验证」四层机制。**

选型结果：

| 方案 | 结论 | 理由 |
|---|---|---|
| `flutter_screenutil`（社区最流行） | **否决** | `.sp` 与系统 `TextScaler` 叠加，在 Flutter 3.16+ 的**非线性缩放**下结果不可预测；尺寸写成 `.w/.h` 后脱离约束系统，缩放系数在分屏 / 折叠屏 / 多窗口下失效；尺寸来源与 Design Token 体系分裂。详见 §2 |
| `responsive_framework` | **否决** | 核心价值是断点包装，其 `autoScale` 档同样是缩放；断点常量自建成本约 10 行，不值得引依赖 |
| `flutter_adaptive_scaffold`（flutter/packages 官方仓库维护） | **不引入（改为自建）** | 它提供的断点常量、插槽布局在本案中可用性有限：窄屏的 `primaryNavigation` 收进 Drawer，底部导航栏仍需自写（§4 L2）；分栏比例需按本案规则传参；折叠屏铰链避让不提供（§6.4）。**封装它所需的工作量与直接自建相当**，中间层反而增加一层需要对齐的语义。故自建 `AppShell`（`lib/app/layout_shell.dart`），不引入该依赖 |
| `window_size_classes` | 不采纳 | 许可为 LGPL-3.0，商用引入需法务确认；功能已被本案自建断点覆盖 |
| `auto_size_text` | **不采纳** | 其语义是"收缩字号以适应容器"，会把系统放大后的字号缩回去，**抵消字号放大的无障碍效果**（§4 L4）。金额的自适应由离散字号档 + 容器自适应承担 |
| 自建断点常量 + 布局壳 + 约束层 + 矩阵验证 | **采纳** | 见 §3、§4 L2/L3、§7。断点常量在 `lib/app/breakpoints.dart`，壳层在 `lib/app/layout_shell.dart` |

**「一劳永逸」的正确含义**：一次性建好四件事，之后每个页面确实只写一次。不是找一个包，把尺寸问题交给魔法系数。但"只写一次"有明确的**职责边界**——壳层负责导航与一级分栏，栏数在 2 以上的页内分区由页面自己用约束处理。边界见 §4 L2。

**三条设计边界**（贯穿全文，是各节取舍的共同依据）：

- **窗口宽度 ≠ 容器可用宽度**，两者用不同的数据源判断（§3.3）；
- **壳层只承担一级导航与一级分栏**，页内分区由页面自行决策（§4 L2）；
- **破版来自维度组合**，验证必须覆盖"窄屏 × 大字号 × 长文案"的乘积，而非各自独立的用例（§7.2）。

## 2. 为什么否决整体等比缩放（关键判断）

`flutter_screenutil` 的做法是以设计稿尺寸（如 375×812）为基准计算缩放系数，所有尺寸写 `.w` / `.h`、字号写 `.sp`，运行时按屏宽等比放大。它在**单一手机形态 + 不放大系统字号**的前提下可用，本案不满足这两个前提。

三条理由，按"被反驳的难度"排序：

**其一，与系统字体缩放叠加，结果不可预测（最强理由）。** `.sp` 已经在按屏宽缩放字号，用户再把系统字号调大，两者相乘。更麻烦的是 Flutter 3.16 起系统传入的 `TextScaler` 是**非线性**的（Android 14+ 与 iOS 在放大区间的增长曲线经过压缩），与 `.sp` 的线性放大相乘后，最终字号没有可预期的表达式。无障碍场景（视力不佳的用户把系统字号调到最大）会直接破版。

**其二，尺寸脱离约束系统，缩放系数在分屏 / 折叠 / 多窗口下本身失效。** Flutter 的布局系统是约束驱动的——组件拿到多少空间就排多少内容。改写成"所有尺寸乘系数"等于把这个能力关掉，换成手写比例计算。而分屏、折叠屏展开、Slide Over 下，**可用宽度的变化不由屏幕尺寸决定**，系数算出来的值就是错的。

**其三，尺寸来源与 Design Token 体系分裂。** 一旦部分尺寸走系数、部分走 Token，就会出现"这个 padding 该写 16 还是 16.w"的日常歧义，改一处漏一处。

**一个可验证的判据**：如果界面在"字体超大 + 屏幕超宽"两个极端下仍然可用，说明用的是约束驱动；如果其中一个极端就崩，说明用了缩放。**正文文字在手机与平板上应该是同一个可读尺寸**，变的只有容器宽度与栏数——这是本案与缩放派的根本分歧。

**需要说明的两点**：

- 上述第一条推论"平板会变成大号手机"需要限定——带缩放系数钳制的实现不会出现 14sp 放大到 38sp 这么极端的情况。真正的问题是：即便钳制了系数，在 1024dp 宽度下**卡片与字号同时放大**仍会挤压信息密度，与 PRD「平板不是放大的手机」的方向相反。这是待实现后验证的推论，不是已证结论。
- **本判断的适用范围是"四端（手机 × 平板）× 尊重系统字体缩放"。** 若产品只做单一手机形态、且不需要跟随系统字号，"设计稿等比缩放"是可用且成本更低的方案。本案否决它，是因为这两个前提都不成立。

## 3. 断点定义（唯一来源）

### 3.1 宽度档位

| 尺寸类 | 宽度范围 | 本案典型设备与场景 | 布局形态 |
|---|---|---|---|
| compact | < 600dp | 手机竖屏（320–430）；**平板 1/2 分屏（320–520）** | 底部 NavigationBar · 单栏 |
| medium | 600–839dp | 手机横屏；**iPad mini 744 / 10.9″ 820 / Air 11″ 820 / Pro 11″ 834 竖屏**；12.9″ 的 1/2 分屏（683）；折叠屏内屏（673–841） | NavigationRail（收起）· 单栏 |
| expanded | 840–1199dp | **12.9″ / 13″ 平板竖屏（1024）**；主流平板横屏；折叠屏展开（841，压线） | NavigationRail（展开）· 双栏 |
| large | ≥ 1200dp | 大平板横屏（1366） | Rail（展开 + 图标文字）· 双栏 |

**iPad 竖屏的档位归属**：除 12.9″ / 13″（1024dp）外，iPad 竖屏宽度都在 744–834dp 之间，属 **medium** 档，形态是"Rail（收起）+ 单栏"，**不是双栏**。这一点同时影响开发与设计：设计侧交付的"iPad 竖屏稿"应对应单栏形态。

**关于 Material 3 的 extra-large（≥ 1600dp）**：本案并入 large，不单设档。理由：四端范围内不存在该宽度的物理设备，该区间只可能在桌面端多窗口或外接显示器时出现；极宽屏上的可读性由内容限宽（§4 L4）负责，不需要额外的布局形态。测试矩阵中**保留一个 ≥ 1600 的视口**（V10），用于验证限宽居中确实生效。

### 3.2 高度档位

| 高度类 | 范围 | 对应场景 |
|---|---|---|
| compactHeight | < 480dp | 手机横屏；分屏中的矮窗口 |
| regular | ≥ 480dp | 其余 |

高度类的**消费方仅限记账输入页**（形态 B 的判据，见 §6.1）。其余页面在 compactHeight 下维持宽度档对应的形态，垂直空间不足时以滚动兜底。

### 3.3 判断分两层

`MediaQuery.sizeOf(context)` 返回的是**当前窗口**的尺寸，不是物理屏幕尺寸。在 iPad 分屏、Slide Over、多窗口下，它返回的正是被系统压缩后的窗口宽度——**在窗口级判断上它是正确且官方的工具**。

它会出错的地方是在**嵌套容器内**判断局部空间：双栏布局的右栏、`Drawer` 内部、嵌套列表里，这些位置的可用宽度由父级约束决定，与窗口宽度无关。

因此规则分两层，各司其职：

| 判断对象 | 数据来源 | 用途 |
|---|---|---|
| **窗口尺寸类** | `MediaQuery.sizeOf(context).width` | 决定**壳层**：底部导航 vs Rail、单栏 vs 双栏、页面级留白的档位 |
| **容器内可用宽度** | `LayoutBuilder` 的 `constraints.maxWidth` | 决定**页面内**：这个容器里放几列、要不要换行、内部分区怎么切 |

**纪律**：`lib/features/**` 不得直接调用 `MediaQuery.size` / `MediaQuery.sizeOf`。窗口级判断走 `sizeClassOf(context)`，容器级判断走 `LayoutBuilder`。

这条禁令的落点是**限制该 API 的使用位置**——避免"窗口宽度被当作容器宽度"这类错误——而非否定它本身。区分清楚后，壳层可以放心地用它。

### 3.4 常量归属

断点数值只允许定义在 `lib/app/breakpoints.dart` 一处。任何地方出现字面量 600 / 840 / 1200 / 480 视为缺陷（理由与 Design Token 相同：散落即失效）。

该文件提供两级取值工具（窗口级 `sizeClassOf` / `responsiveValue`，容器级 `sizeClassFromConstraints` / `responsiveValueOf`），页面内不得自行判断数值区间。`Breakpoints.compactHeight` = 480 与 `isFormB(width, height)` 同样定义在此，供记账输入页的形态判据（§6.1）直接调用。

**本案不引入 `flutter_adaptive_scaffold`**（理由见 §1），因此不存在与三方包常量对齐的问题。若后续有引入同类包的需求，必须遵守的原则是：**以本案自建常量为准，通过参数显式传入，不引用包的常量**——断点数值是难逆的布局契约，控制权不交给非 SDK 核心的依赖。

## 4. 四层适配机制

### L1 断点层

`Breakpoints` 常量 + 两级取值工具：

```dart
enum SizeClass { compact, medium, expanded, large }

class Breakpoints {
  Breakpoints._();
  static const double compactMax = 600;   // compact | medium
  static const double mediumMax  = 840;   // medium  | expanded
  static const double expandedMax = 1200; // expanded| large
  static const double compactHeight = 480;

  static SizeClass sizeClassFromWidth(double width) { /* ... */ }
}

// 窗口级：决定壳层
SizeClass sizeClassOf(BuildContext context);

// 容器级：决定页面内布局
SizeClass sizeClassFromConstraints(BoxConstraints constraints);

// 离散取值（窗口级 / 容器级各一份）
T responsiveValue<T>(BuildContext context, {
  required T compact, T? medium, T? expanded, T? large,
});
T responsiveValueOf<T>(BoxConstraints constraints, {
  required T compact, T? medium, T? expanded, T? large,
});
```

> **归属**：以上全部定义在 `lib/app/breakpoints.dart`。`sizeClassFromConstraints` 和 `responsiveValueOf` 是容器级工具，供页面在 `LayoutBuilder` 内使用。

**`responsiveValue` 的边界**：

它用于**离散令牌的选择**——从一组预设值里挑一个：栏数（1 / 2 / 3）、内边距档（16 / 24 / 32）、字号档（48 / 56 / 64）、某个装饰性元素显示与否。

**禁止用它做连续推导**——不允许用它算出"由宽度线性映射的尺寸"，例如 `width / 375 * 100.0`。那是缩放的变体。

判据不在"是不是尺寸"（内边距和字号本身就是尺寸），而在"**是从预设集合里选，还是从宽度推导**"。

### L2 布局壳层（"一劳永逸"的核心）

**先说职责边界**：

壳层不能装下所有排布逻辑——报表页三栏、资产页双列、记账页左右分栏都超出壳层能力范围。边界如下，**不要扩大壳的承诺**：

| 层 | 负责 | 不负责 |
|---|---|---|
| **壳层**（`lib/app/layout_shell.dart`） | 一级导航形态（底栏 / Rail）；一级分栏（正文 + 上下文详情）；内容限宽的施加位置；安全区与键盘避让 | 栏数 ≥ 2 的页内分区；非标准分栏（记账页左右分栏）；页内多列网格 |
| **页面** | 上述"不负责"的部分，用 `LayoutBuilder` 的约束自行决策（L3 第 1 条） | 一级导航与一级分栏 |

**插槽定义与形态**（对齐 `AppShell` 的构造参数）：

| 插槽 | 语义 | compact | medium | expanded | large |
|---|---|---|---|---|---|
| 一级导航 | 一级入口 | 底部 NavigationBar | Rail（收起 · 仅图标） | Rail（图标 + 下方文字） | Rail（展开宽带 · 图标文字） |
| `body` | 主内容（流水列表、报表图表） | 全宽 | 全宽（限宽 840） | 左栏 | 左栏 |
| `secondaryBody` | 上下文详情（账单详情、筛选面板） | 空（走独立页面） | 空（走独立页面） | 右栏 | 右栏 |
| **页面内二次分区** | 报表三栏、资产双列等 | — | — | 由页面自行实现 | 由页面自行实现 |

**`secondaryBody` 为空时的占位**：expanded / large 档下，若右栏无内容（未选中账单），显示居中的空态占位——图标 + 「选择左侧条目查看详情」提示，不显示空白面板。

**实现提示（避免踩坑）**：

1. **compact 档的底部导航栏由壳层自行实现。** 本案不走三方插槽包，两套导航（底栏 / Rail）都在 `AppShell` 内按 `SizeClass` 分支写出，不依赖任何"自动切换"。
2. **`NavigationRail` 的参数有互斥约束**：`extended: true` 与 `labelType: all` 不能同时使用（框架有断言）。本案的对应关系是：

   | 档位 | `extended` | `labelType` | 视觉 |
   |---|---|---|---|
   | medium | false | `none` | 仅图标 |
   | expanded | false | `all` | 图标 + 下方文字（收起态） |
   | large | true | `none` | 展开宽带 + 图标文字 |

3. **折叠屏铰链避让不由壳层包提供**，见 §6.4。

**分栏比例**：

采用**等比例分栏**——`Row` 内两个 `Expanded`（详情栏出现时），中间以 `VerticalDivider` 分隔。

```
列表（body）栏宽 = 可用宽度 × 0.5
详情（secondaryBody）栏宽 = 可用宽度 × 0.5
```

选等比例而非固定列表栏的理由：实现最简单、无参数、在各档下行为可预期，且与 `Expanded` 的约束语义一致（两栏按剩余空间均分，父级约束变化时自动重算）。**已知代价**：在 1200dp 以上，列表栏会被拉到 600dp 以上，超过列表类内容约 840dp 的可读上限——若实际使用中出现列表行过宽、视线回扫吃力，改法是给列表栏加 `ConstrainedBox(maxWidth: 840)` 并让剩余空间归详情栏，属局部调整，不影响壳层接口。

当 `secondaryBody` 为 null 时（compact / medium 档，或未选中详情），`body` 独占整宽，不做分栏。

### L3 约束层（写页面的唯一纪律）

**第 1 条 · 组件只响应"给了我多少空间"，不响应"屏幕多大"。** 用 `LayoutBuilder` 的局部约束做内部决策。

**第 2 条 · 窗口级判断与容器级判断分开**（见 §3.3）。窗口类走 `sizeClassOf`，容器内走 `LayoutBuilder`；`lib/features/**` 不得直接调用 `MediaQuery.size`。

**第 3 条 · 超宽屏内容限宽（分层，见 L4 限宽表）。** 限宽装饰**只作用于单栏页面**。

**第 4 条 · 弹性优先。** `Flexible` / `Expanded` / `Wrap` 替代固定宽高；`Row` 中的可变长文本必须包 `Expanded` 或 `Flexible`。

**第 5 条 · 可变长文本必填 `maxLines` + `overflow`**（备注、分类名、账户名）。三处硬约束叠加（长备注 × 字体最大档 × 系统缩放 2.0）是溢出报错的主要来源。

### L4 密度与排版层

**不做连续缩放，只做离散档位。**

| 项 | 规则 |
|---|---|
| 正文字号 | **`AdaptiveFontSizes`（`lib/app/breakpoints.dart`）**：正文 15sp、辅助信息 12sp、标题 17sp——**全断点固定**。注：这是自适应页面工具字号；设计令牌字阶（body 16/14/12、title 22/16/14）见《12》§6.2，二者并存、用途不同 |
| 展示型字号（记账页大金额） | **`AdaptiveFontSizes.display`** 离散三档：compact 48 / medium 56 / expanded 64（large 沿用 64）。**不是**《12》的 `amountL=32` |
| 页面内边距 | 离散三档：compact 16 / medium 24 / expanded 32（large 沿用 32） |
| 卡片内边距 | 离散三档：compact 12 / medium 16 / expanded 20 |
| VisualDensity | 统一 **`standard`**，不使用 `comfortable`（理由见下） |
| 触控目标 | 按**平台**区分：Material 最小 48×48dp、iOS 最小 44×44pt；相邻可点区域间距 ≥ 8dp |
| 系统字号缩放 | `MediaQuery.withClampedTextScaling(minScaleFactor: 0.8, maxScaleFactor: 2.0)` |
| 图标与图片 | 矢量优先；位图提供多倍图 |
| `resizeToAvoidBottomInset` | 记账页（自绘键盘）：**false**；常规页（系统键盘）：**true**。不全局统一 |

**关于 `VisualDensity`**：本案统一使用 `standard`，不使用 `comfortable`。理由是 `comfortable` 会**增大**控件的最小尺寸与间距，平板本就宽裕的横向空间被进一步稀释，一屏可见条目数反而减少——与"平板应提供更高信息密度"的目标相反。密度增益由断点档位（更多栏、双列网格）提供，不由控件膨胀提供。

**关于触控目标**：按**平台**区分，不按设备区分。Material 最小 48×48dp、iOS 最小 44×44pt；这分别是两平台的系统下限，平板没有理由把目标改小。相邻可点区域间距 ≥ 8dp。

**关于系统字号缩放**：

实现方式：使用 Flutter 官方的 `MediaQuery.withClampedTextScaling(...)`，作用于 App 根部（`MaterialApp` 外层）。

**不要**自行实现为 `copyWith(textScaler: TextScaler.linear(x))`——Flutter 3.16 起系统传入的 `TextScaler` 是**非线性**实现（Android 14+ 与 iOS 的大字号增长曲线经过压缩）。用线性实现替换，会把这条曲线压平，导致大字号区间排版突变——正是 §2 批评缩放派的那个毛病。

取值依据：上限取 **2.0**。iOS Dynamic Type 最大档约 3.1×、Android 约 2.0×，钳到更低的值意味着重度视力用户几乎得不到放大，与无障碍要求冲突；Material 的无障碍基准是支持到 200%。下限取 **0.8**，避免把"想调小字号"的用户强制放大。

代价：放大上限放宽后，所有页面都必须在 2.0× 下不破版。这是 L3 各条纪律与 §7 验证用例的目标。**验收标准：记账输入页与流水页在 2.0× 下功能完整、无溢出（允许垂直滚动）。**

若团队评估后认为该代价不可接受，降回 1.3 必须走 ADR，并在 ADR 中写明无障碍影响与替代方案（例如"关键页提供应用内字号开关"）。

**限宽分层**（L3 第 3 条的展开）：

| 内容类型 | 最大宽度 | 施用于 | 理由 |
|---|---|---|---|
| 列表 / 表格 / 表单（流水、账单详情表单、设置、分类管理、账户管理） | 840dp | 单栏页面 | 一行承载"分类 + 金额 + 日期"，840dp 足够；再宽则视线回扫距离过长 |
| 段落文本（备注详情、说明、引导、协议） | 480dp | 单栏页面 | 中文舒适行长 25–35 字，16sp 下约 400–560dp |
| 图表 / 报表明细 | 1000dp | 单栏页面 | 图表越宽信息量越大，但超宽后数据标签密集不可读；1000dp 是"信息量"与"可读性"的平衡点 |
| 双栏页面的各栏 | **不再叠加限宽** | — | 栏宽已由 §4 L2 的分栏规则决定 |

**关于图表限宽**：图表并非"不设上限"——那与 L3"阅读舒适"的原则矛盾，1300dp 宽的饼图扇区标签会挤成一团。故限宽 1000dp；超出时允许横向滚动或缩略展示。

**限宽与分栏互斥**：要求"expanded 档内容限宽 840"与"expanded 档流水页双栏"是两条会互相冲突的规则——在 840–1199dp 区间，840 的限宽会把双栏各栏压到约 380dp（比手机单栏还窄）。因此规定：**限宽装饰只在单栏页面上生效**。

## 6. 需要提前设计的特殊场景

这些是"后期返工重灾区"，必须在 V1.0 设计阶段定方案。

### 6.1 记账输入页的形态判据

形态 B（左右分栏）的触发条件是**析取式**：

```
形态 B  ⟺  height < 480dp  ∨  width >= 600dp
形态 A  ⟺  其余
```

**为什么必须写成析取式**：若按**宽度**单条件列形态（compact → 形态 A），会与《02-PRD》§5.1 的判据分叉——PRD 对形态 B 的定义是"高度 < 480dp **或** 宽度 ≥ 600dp"。两者在 **iPhone SE 横屏（568×320）** 上给出相反结论：宽 568 < 600（按宽度判为形态 A），高 320 < 480（按 PRD 判为形态 B）。同一台设备两个答案，开发到这里会卡住。

本案**以 PRD 为准**——它表达的是用户意图：垂直空间不够时就不能再上下堆叠。同时把 568×320 列为固定回归视口（§7.1 的 V5）。

形态定义与验收沿用《02-PRD》§5.1（STORY-1.1「页面结构」）：

- **形态 A · 竖屏手机**：自下而上四区。
- **形态 B · 横屏与平板**：左右分栏——左区「金额显示 + 计算器键盘」（排在拇指可及范围内），右区「分类宫格 + 属性栏」；宽度 ≥ 840dp 时右区再展开为「宫格 + 属性栏」两列。
- **共同约束**：四区功能不缺失、不折叠进二级页面；金额键盘与分类宫格必须同屏可见、无需滚动；两形态共享同一套组件与状态，**切换不重建页面**（机制见 §6.3）。

**窄高场景（如 iPhone SE 横屏 568×320）的键盘降级**（v2.1 补充）：形态 B 左区宽度可能仅 ~280dp，四列键盘的键帽宽度会不足 60dp（低于触控下限）。处置：

- 键帽宽度 < 56dp 时，键盘列数降为 3（数字 + 运算符合并行），或缩小间距至 2dp；
- 金额显示字号在 compactHeight 下降一档（48 → 36）；
- 分类宫格从 4 列降为 3 列，保证每个键帽 ≥ 48dp。

**剩余动作**：《03-交互原型.html》补一格横屏 / 平板态原型（设计侧）。

### 6.2 键盘、输入设备与 insets

三件事必须分别处理：

**其一，自绘键盘与系统键盘的行为不同。** 记账页的主键盘是自绘的，不触发 `viewInsets`；属性栏的备注输入触发系统键盘，会改变 `viewInsets`。**两套键盘的布局行为不同，必须分别验证**——这是很容易出错的点。

**其二，物理键盘与自绘键盘的互斥策略。** 连接物理键盘（iPad 妙控键盘、蓝牙键盘）时，记账页**不自动弹出自绘键盘**，但仍保留手动唤出入口。判定方式：监听 `HardwareKeyboard` 的连接状态；**不使用屏幕宽度做判定**。不定义这条会出现"两个键盘同时显示"的问题。

**其三，快捷键与屏幕宽度无关。** 把"N 记账、/ 搜索"列在 expanded / large 档是分类错误：快捷键能否使用取决于**是否连接物理键盘**——手机接蓝牙键盘同样应支持，平板不接键盘也按不出来。

处置：`Shortcuts` / `Actions` 在应用层常驻注册，**不设断点条件**。清单：`N` 新建记账、`/` 聚焦搜索（《01-需求梳理》§七）。

`resizeToAvoidBottomInset`：记账页（自绘键盘）与常规页（系统键盘）分别设定，不全局统一。

### 6.3 断点切换的状态保持

**要求**：旋转屏幕、折叠屏展开 / 折叠、进入分屏时，**页面不重建**；滚动位置、未保存草稿、已选属性、输入焦点必须保留。对应《02-PRD》AC7。

Flutter 侧有三件事会破坏这条要求，必须逐条防住：

**一、状态必须上提。** 页面级可变状态（草稿金额、已选分类与属性、滚动位置、筛选条件）由 controller / provider 持有，widget 层保持无状态。只要这一点成立，widget 树被重建也不会丢数据。

**二、树结构必须稳定。** **禁止**写成 `if (isWide) return FormB(); else return FormA();`——两棵树的 Element 结构不同，Flutter 会销毁旧 `State`、创建新 `State`。做法二选一：

- 两形态共用同一 `GlobalKey`；
- 用 `IndexedStack` / `Offstage` 让两形态的子树常驻，只切换可见性。

**三、焦点与输入法连接要保持。** `FocusNode` 由 controller 持有、在页面销毁时才释放，不要放在会被重建的 widget 里；形态切换后若原焦点在备注输入上，需显式恢复焦点。

**验证**：自动化用例——切换 `tester.view.physicalSize` 触发断点变化后，断言 controller 中的草稿与已选属性未变、`FocusNode.hasFocus` 仍为 true、滚动 offset 未归零。

### 6.4 折叠屏与分屏

**信息来源**：`flutter_adaptive_scaffold` 不在技术栈内（§1），且它本身也不提供读取铰链位置或绕开铰链的 API。Flutter 中折叠屏的结构信息来自：

```dart
final features = MediaQuery.of(context).displayFeatures; // List<DisplayFeature>
```

每个 `DisplayFeature` 提供 `bounds`（铰链 / 折叠区在屏幕坐标系中的矩形）与 `orientation`（水平 / 垂直）。

**处置策略**：

- 在壳层内计算"可用内容区 = 窗口尺寸 − 铰链占位"，并在该区域内做分栏决策；
- 竖直铰链（`orientation == vertical`）时，双栏分界**不得落在铰链区域内**；无法避开时退化为单栏 + 上下分区；
- 该能力**需自建**（`HingeAwareLayout`），工作量计入开发早期，**不要排到后期**；
- 无真机阶段，铰链宽度按 0–48dp 的保守值近似处理。

**分屏**：分屏下的窗口宽度由系统给出，壳层按 §3.1 的断点正常判定即可。注意**分屏的典型宽度落在 320–683dp，多数走 compact 档（底部导航 + 单栏）**，而不是双栏——640dp 这类宽度在真实分屏中不出现，它实际对应"小平板竖屏"（已在 §7.1 由 V7 覆盖）。

**压线设备**：部分折叠屏内屏展开宽度为 **841dp**，恰好越过 expanded 的 840dp 边界。这类设备在展开瞬间会切换布局形态，需在真机上验证切换是否平滑、状态是否保持。

### 6.5 安全区与 insets

Flutter 里对应"安全区"的有三个不同的量，用途不同，混用会出 bug：

| 量 | 含义 | 用途 |
|---|---|---|
| `MediaQuery.viewPadding` | 系统 UI 的**常驻**占位（状态栏、Home Indicator、导航栏）。**不随键盘变化** | 静态布局：底栏高度、页面上下留白的下限 |
| `MediaQuery.viewInsets` | 被**临时**遮挡的部分（主要是键盘） | 动态避让：输入框顶起、内容上移 |
| `MediaQuery.padding` | viewPadding 减去正在被 viewInsets 吃掉的部分 | **不要**用它算底栏或键盘高度——键盘弹出时 `padding.bottom` 会变成 0，底栏会"跳"一次 |

**四种底部形态都要验证**：

| 平台 | 形态 | 预期 `viewPadding.bottom` |
|---|---|---|
| iOS | 全面屏（Home Indicator） | 约 34dp |
| iOS | 带 Home 键机型 | 0 |
| Android | 手势导航 | 约 24dp |
| Android | 三键导航 | 约 48dp |

**Android 15 起的强制 edge-to-edge**：targetSdk 35 起，应用默认进入 edge-to-edge，系统栏变透明、内容延伸到系统栏之下，`viewPadding` 的取值行为与旧版本不同，**必须自行处理 insets**。这与"三键导航"叠加时是最容易出问题的组合（底部同时有导航栏与手势条），需在 Android 15+ 真机上单独验证。

**平板**：`viewPadding.bottom` 可能为 0，**布局不能依赖它恒大于零**。

### 6.6 小组件适配（原生侧，按平台拆开）

小组件不属于 Flutter 布局范围，但属于"屏幕适配"的交付内容。这部分由 D2 小组件桥负责，实现前需按下表逐项确认。

**iOS（WidgetKit）**

| 项 | 要求 |
|---|---|
| 尺寸族 | 桌面：`systemSmall`（2×2）、`systemMedium`（4×2）；PRD 另有锁屏与 Action Button 入口 → 需覆盖 `accessoryRectangular` / `accessoryCircular` / `accessoryInline` |
| iOS 17+ 强制项 | 必须使用 `.containerBackground(for: .widget)`，否则在 iOS 17+ 上渲染异常 |
| 字号 | WidgetKit 对 Dynamic Type 的支持受限，需在固定尺寸内定义离散字号档，并按可用的 `.dynamicTypeSize` 环境值降级 |
| 深色模式 | 使用 asset catalog 的 Any / Dark 变体，不在代码里硬编码颜色 |
| 多语言 | 文案长度变化会撑破固定尺寸，中英文各出一套最长文案验证 |

**Android（AppWidget）**

| 项 | 要求 |
|---|---|
| 尺寸声明 | API 31+ 用 `targetCellWidth` / `targetCellHeight` 声明期望格数；`minWidth` / `minHeight` 按 `70n − 30` 换算 |
| 可调整尺寸 | 声明 `resizeMode`；PRD 要求 1×4 与 2×2 两种，需分别提供布局 |
| API 34+ | `AppWidgetManager` 的 `OPTION_APPWIDGET_SIZES` 会返回可用尺寸列表，布局需按**实际**尺寸选择，不能假定只有声明的那两种 |
| RemoteViews 限制 | 不支持自定义字体、不支持任意 View；字号只能用系统字体，**不能依赖设计稿字体做适配** |
| 启动器差异 | 4×5 / 5×5 / 5×6 网格下同一声明格数的实际像素不同 → 布局必须自适应（权重布局），**禁止绝对定位** |
| 深色模式 | 用 `values-night` 资源，不在代码里判断 |

## 7. 验证方案

没有验证机制的适配方案等于没有方案——破版只会被用户发现。

v1.0 的验证设计有两个问题：视口选得不代表真实场景；把"尺寸矩阵"与"字体极端"当成两个独立用例，而破版实际来自两者的**乘积**。v2.0 一并修正。

### 7.1 视口矩阵（12 个）

| 编号 | 视口（逻辑像素） | 覆盖场景 | 尺寸类 |
|---|---|---|---|
| V1 | 320 × 568 | 小屏手机竖屏下限 | compact |
| V2 | 390 × 844 | 主流手机竖屏 | compact |
| V3 | 430 × 932 | 大屏手机竖屏 | compact |
| V4 | 844 × 390 | 手机横屏 | medium + compactHeight |
| V5 | 568 × 320 | 小屏手机横屏 —— **形态判据冲突用例（§6.1），必测** | compact + compactHeight |
| V6 | 417 × 1194 | iPad 11″ 1/2 分屏（窄宽 + 平板高） | compact |
| V7 | 768 × 1024 | 小平板竖屏 | medium |
| V8 | 1024 × 768 | 平板横屏 / 12.9″ 竖屏 | expanded |
| V9 | 1366 × 1024 | 大平板横屏 | large |
| V10 | 1600 × 1000 | 超宽屏（验证限宽居中与 extra-large 合并策略） | large |
| V11 | 673 × 841 | 折叠屏展开（Z Fold 系内屏） | medium |
| V12 | 841 × 701 | 折叠屏展开（Pixel Fold 内屏，**压线 ≥ 840**） | expanded（边界抖动） |

**与 v1.0 的差异及理由**：

- **删除** v1.0 的 V8（640×900，"分屏窄条"）：640dp 宽度在真实分屏中不出现。分屏的主战场是 320–683dp，多为 compact 档（底部导航 + 单栏），与 640 所在的 medium 档是**不同的布局分支**。640 一类宽度实际对应"小平板竖屏"，已被 V7 覆盖。
- **新增** V5 / V6 / V11 / V12 / V10：分别对应形态判据冲突、真实分屏、折叠屏展开、边界抖动、超宽限宽。

### 7.2 组合采样（v1.0 缺失）

破版来自维度组合，不是单一维度。方案 L3 第 5 条自己就写了"三处硬约束叠加是溢出报错的主要来源"——但 v1.0 的验证方案把矩阵与字体做成了两个独立用例，没有覆盖组合。

全组合（12 视口 × N 字体档 × M 文案长度）在 CI 上不可行，因此分两级：

**PR 门禁（12 个组合）**：视口 {V1, V5, V6} × 字体缩放 {1.0, 2.0} × 文案 {常规, 最长备注} = 3 × 2 × 2。

选这三个视口的理由：V1 是最窄宽度，V5 是形态判据的冲突点，V6 是"窄 + 高"的分屏组合，三者互不覆盖。

**PR 门禁的页面范围**（v2.1 补充）：只测**记账输入页 + 流水页**——两者是溢出高发区（键盘 × 分类宫格 × 金额显示 × 可变长文本）。其余页面在 nightly 全矩阵中覆盖。

**Nightly（全矩阵）**：12 视口 × 字体 {1.0, 1.3, 2.0} × 页面关键态。

### 7.3 自动化

**其一，多尺寸 golden**：用 `tester.view.physicalSize` 驱动，按 §7.2 的矩阵渲染关键页面。

**golden 的宿主一致性（v1.0 缺失，必须补）**：golden 的像素结果**依赖运行平台**（字体光栅化、抗锯齿实现不同）。在 macOS 开发机生成的基准拿到 Linux CI 上比对，会产生大量与代码无关的假阳性。处置：

- 基准 golden **必须在 CI 所用的同一平台生成**，本地不生成、不比对；
- 用标签隔离（如 `@Tags(['golden'])`），本地默认跳过，CI 单独执行；
- **中文字体必须显式加载**：CI 容器通常不含中文字体，中文会渲染成空白方框——golden 全绿但测的是空白。需通过 `FontLoader` 加载并入仓的字体文件（如 Noto Sans SC 子集）。

**其二，溢出即失败**：Flutter 的 `RenderFlex overflowed` 在 `flutter_test` 中会由 binding 记为待处理异常，测试结束时未处理即判失败，**无需额外断言**。注意例外：若测试代码中调用了 `tester.takeException()`，该异常会被消费掉，断言链失效。

**其三，状态保持用例**：按 §6.3 的验证方法，切换视口后断言 controller 状态、焦点、滚动位置。

**其四，CI 门禁**：在《05-开发规范》§5.2 的门禁序列中，`flutter test test/adaptive/` 执行 §7.2 的 PR 组合；全矩阵在 nightly 流水线执行。

### 7.4 人工验收（自动化覆盖不了的部分）

- **折叠屏真机**：展开 / 折叠过程中的状态保持（§6.3）、铰链区域是否被内容覆盖。
- **iPad 分屏 / Slide Over**：切换窗口大小、拖拽分栏。
- **Android 15+ 三键导航真机**：edge-to-edge 下的 insets 表现（§6.5）。
- **系统字体最大档（2.0×）下的记账闭环**。

## 11. 术语与参数对照（开发用）

| 本文术语 | Flutter / 三方包对应 |
|---|---|
| 尺寸类 compact / medium / expanded / large | 自定义 `SizeClass`（`lib/app/breakpoints.dart`） |
| 窗口级判断 | `MediaQuery.sizeOf(context).width`（仅在壳层，经 `sizeClassOf` 封装） |
| 容器级判断 | `LayoutBuilder` 的 `constraints.maxWidth` |
| 内容限宽 | `ContentWidthConstraint`（`maxWidth` 默认 840）；列表类 840 / 文本类 480 |
| 系统字号缩放钳制 | `MediaQuery.withClampedTextScaling(minScaleFactor: 0.8, maxScaleFactor: 2.0)` |
| 铰链信息 | `MediaQuery.of(context).displayFeatures` |
| 静态安全区 | `MediaQuery.viewPadding` |
| 键盘避让 | `MediaQuery.viewInsets` |
| 断点切换不重建 | 状态上提到 controller + `GlobalKey` / `IndexedStack` |
| 物理键盘检测 | `HardwareKeyboard.instance` |
| 快捷键注册 | `Shortcuts` / `Actions`（应用层常驻，不设断点条件） |
| 一级分栏 | `AppShell.secondaryBody`（等比例 `Expanded` × 2） |
