## 1. 背景与机会

个人记账是亿级用户规模的工具赛道，当前形成三个阵营：以钱迹为代表的极简免费派（600 万用户、¥36/年·¥128 买断）、以随手记/挖财/鲨鱼为代表的老牌广告派、以商汤咔皮（6 个月百万用户）为代表的 AI 无感记账新势力。赛道存在结构性空位：**没有一个产品同时做到「AI 能力 + 数据自由（本地优先 + 导出 + WebDAV）+ 无广告 + 四端一致体验」**。本产品以此组合切入，免费层对标钱迹的诚意，付费层以四端云同步为主付费点，叠加 AI Pro 与家庭计划构成五层变现结构（详见《01-需求梳理》第十章）。

本文不复述调研过程与决策依据，仅输出可执行规格。所有「为什么」层面的论证见《01-需求梳理.md》。

## 2. 目标与成功指标

产品总目标：12 个月内成为「AI 记账 + 数据自由」组合定位的头部独立产品；V4.0 跑通付费模型。

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| 次日留存 | ≥ 40% | 埋点：D1 回访 / 新增激活 |
| 30 日留存 | ≥ 20% | 同上 D30 口径 |
| 月活跃记账天数 ≥ 15 的用户占比 | ≥ 35% | 埋点：月内 distinct 记账日分布 |
| 人均日记账笔数 | ≥ 3 | 埋点：日记账事件均值 |
| 付费转化率（V4.0 后） | ≥ 3% | 付费用户 / 月活 |
| V1.0 商店评分 | ≥ 4.7 | App Store + 主流安卓商店 |
| **V2.0 规则引擎套用耗时（新增）** | ≤ 3s / 1000 笔 | 性能埋点（后台 isolate） |
| **V3.0 净值可追溯率（新增）** | 100% | 每项资产/负债均可下钻到明细 |

**分阶段唯一目标**（功能决策冲突时以此裁决）：

- **V1.0**：留存与口碑（付费墙未上线）。
- **V2.0**：把「省力」做到同类最优——规则引擎与提醒中心是核心。
- **V3.0**：把「看清自己有多少钱」做实——净值可信、方法论可选。
- **V4.0**：付费转化。**V2.0/V3.0 期间不设任何付费触点**（含 AI 额度用尽提示），只做提示不做推销。

## 3. 用户与场景

五类画像（详细论证见《01-需求梳理》第二章）：P1 效率型个人（52%，核心服务对象）、P2 管理型家庭（28%，V4.0 付费主力）、P3 极客隐私型（10%，口碑放大器）、P4 情绪价值型（5%，点购人群）、**P5 资产管理型（5%，V3.0 目标人群，v1.5 新增）**。

V1.0 MVP 的设计主对象是 P1，约束条件是「不伤害 P3」（即本地优先、不强制注册）。V2.0 继续服务 P1/P2，V3.0 首次为 P5 设计（投资持仓、贷款摊销、资产折旧）。

## 4. 范围

**V1.0 范围内**：手动记账核心闭环（M1，除附件）、账户（M2 基础）、基础报表（M4.1）、本地存储与手动备份（M7.1/M7.4）、安全与应用锁（M8 全部）、设置与个性化（M9：**F9.2 主题系统（10 套内置）/ F9.1 基础设置**）；手机双端（iOS/Android）首发，平板（iPad/Android Pad）4–6 周内补齐。

> **范围更正（v1.7，以代码为准）**：原写「现金/储蓄卡账户」，但**代码实况是账户类型选择器已开放四类——现金 / 储蓄卡 / 信用卡 / 投资**（`AccountType.enabledInV1`）。因此「信用卡账户」与「投资账户」已提前进入 V1.0 的**账户创建能力**；但信用卡的**欠款余额存储值语义**、账单日/还款日属性组、投资持仓追踪仍归 V2.0/V3.0。两者不矛盾：「能建一个信用卡账户」与「信用卡功能完整」是两件事。

**V1.0 范围外（明确不做，防蔓延）**：云同步（V2.0 架构落地，V4.0 转付费）、多账本/家庭（V2.0/V3.0）、预算（V2.0）、周期记账（V2.0）、AI 识别与周报（**V2.0**）、AI 进阶（订阅检测/人格报告/现金流预测，V3.0）、借贷账户（`loan_out` / `loan_in`，V2.0）、导入导出（V2.0/V3.0）、Widget 之外的自动化记账（V2.0）。凡范围外需求进入排期，一律走需求变更流程。

**V2.0 范围内（v1.5 新增，全部免费）**：交易精度（商户学习、交易类型化、规则引擎、分割交易）、主动管家（信用卡账单周期、对账模式、提醒中心、安全可花）、预算深化（沉淀基金、目标体系）、留存（报销工作流、情绪反馈、游戏化留存）、AI 周报简版；以及 v1.4 已规划的云同步架构、家庭共享基础、多币种、资产总览、导入、OCR。

**V3.0 范围内（v1.5 新增，全部免费）**：资产完整性（投资持仓、贷款摊销、资产折旧、债务优化）、预算方法论（四套切换）、可视化（Sankey、交叉分析、资金年龄）、协作深化（独立登录、归属标记、交易评论、只读分享、AA 结算）、生态（桌面端、开放 API/MCP、扩展导入格式、短信记账预研）、AI 深化（订阅检测、人格报告、现金流预测）。

**G-1 记账月（Accounting Month）**

记账月是由用户设置的「月起始日」定义的统计周期。设起始日为 D，则任一日期 T 所属的记账月为「T 之前最近的 D 号起，至下一个 D 号前一日止」的区间。默认 D=1，此时记账月 = 自然月。

这是全产品唯一的「某笔账单属于哪个月」判定入口。报表、流水分组、预算周期、周期记账、周报/月报、AI 额度重置**一律**以此为准，禁止各处自行按自然月计算。

**G-2.1 账户余额的定义（v1.6 新增）**

前面所有「计入账户余额 = 是」的行，共享同一条恒等式：

> **账户余额 = 期初余额 + Σ(该账户上「计入账户余额 = 是」的账单金额 × 方向)**

方向规则：支出/转出为负，收入/转入为正。信用卡账户按双数模型（见 STORY-2.2）单独处理，其「欠款余额」与账户余额互为负值。

这是全产品唯一的余额口径，适用于**非信用卡账户**（现金 / 储蓄卡 / 投资等）。禁止任何页面自行按「流水累加」或「另存余额字段」实现。这类账户的余额是**派生量**：任何页面需要显示余额时，一律按此式重算；对账（STORY-2.1）本质是**插入一笔调整账单**而非直接改余额值，因此恒等式恒成立。

> **实现状态**：✅ **已实现**。`AccountRepositoryImpl.listWithBalances` 一次 GROUP BY 查询、`balanceOf` 五段式 `期初 − Σexpense + Σincome − ΣtransferOut + ΣtransferIn`，无物化余额列。对账走 `CreateEntryUseCase` 生成 `source='reconcile'` 的凭证账单，恒等式成立。

**信用卡账户的唯一例外（`[待建]`）**：其「欠款余额」设计上是**存储值**（需可被对账直接修正），由账单入账时累加维护，并通过对账页的「聚合校验」保证与账单事实一致。

> ⚠️ **代码实况**：`accounts` 表**没有 `credit_balance_cents` 列**，`balanceOf` 对**所有账户类型**统一走派生计算。因此**当前信用卡也走派生量**，G-2.1 的例外尚未落地。且这不是纯加列——需在余额算法中按 `type='credit'` 分流，属**结构性改动**，归 V2.0。详见《08》§5.3 / §7.2。

### 5.1 EPIC-1 快速记账

**STORY-1.1 手动记一笔**

> As a 效率型用户，我想在 3 次点击内记完一笔支出，这样记账不会成为负担，我能坚持下去。

页面结构（SP-1-01，记账输入页）：**分两种形态，功能完整度必须一致。**

**形态 A · 竖屏手机**（宽度 < 600dp 且高度 ≥ 480dp）：自下而上四区——①金额区（大字号，实时显示表达式与结果）；②计算器键盘（数字 0–9、小数点、+−×÷、退格、确认；支持连续四则运算，等号即结果；表达式超长时字号自适应缩小）；③分类宫格（一屏 8 个，第 9 格固定为「更多」，长按拖动排序）；④属性栏（账户 chip、日期 chip、备注 chip、标签入口 V1.0 隐藏）。

**形态 B · 横屏与平板**（高度 < 480dp，或宽度 ≥ 600dp）：**左右分栏**——左区为「金额区 + 计算器键盘」（排在拇指可及范围内），右区为「分类宫格 + 属性栏」。约束：四区功能不缺失、不折叠进二级页面；**金额键盘与分类宫格必须同屏可见，无需滚动**。平板（宽度 ≥ 840dp）时右区可再展开为「宫格 + 属性栏」两列，属性栏常驻不收起。

**两形态共享同一套组件与状态**：金额键盘（数字/小数点/退格/OK）、分类宫格、「OK 才保存」的行为在两种形态下完全一致，差异仅在于排布。形态切换（旋转屏幕、折叠屏展开 / 折叠、进入分屏）**不重建页面**，未保存的草稿金额与已选属性必须保留。

**v1.5 新增：类型切换条**。记账页顶部新增类型分段控件（支出 | 收入 | 转账 | 借出 | 借入）。默认「支出」。切到后三者时，分类宫格区替换为对应表单（详见 STORY-1.8），并出现「保存」按钮——这是 G-6 的直接落地。

核心交互（v1.x 修订）：**点 OK 保存**——金额键盘仅数字、小数点、退格/清空与 OK（无四则运算）；点分类只预选高亮，**不落库**；按 OK 后账单入账。保存后 toast「已记 ¥25.00」带「撤销」（5 秒窗口），1.5 秒后金额自动清零，光标回到金额区，可连续记账。设置项「保存后退出输入页」默认关闭。

边界与异常（**v1.5 补全**）：

- **金额上限** 99,999,999.99；已达到上限后再输入数字位，忽略该位并触发抖动提示。
- **零值**：金额为 0 时点分类不落库（仅高亮）；但**编辑态**允许保存为 0，保存时给出「金额为 0」的轻提示。
- **小数点后强制两位**；输入第三位小数时忽略。
- **除零**：表达式含 `÷0` 时结果区显示「无法计算」，此时点分类不落库并提示「表达式有误」。
- **表达式长度上限**：连续运算符最多 12 个；达上限后忽略新运算符。

**STORY-1.6 商户自动学习（V2.0，P2/F）——v1.5 新增**

商户名第一次被归入某分类后，第二次出现时自动带出该分类，并以可点击提示呈现「上次归入 餐饮-饮料」，用户可一键改。

**规则**：

- 匹配：先精确匹配商户名，再退化到前缀匹配（≥ 4 字重合），均不命中则不联想。**不做模糊 AI 推断**（保持确定性）。

- **与规则引擎（STORY-6.1）的执行顺序（v1.6 明确）**：

  | 阶段 | 执行者 | 说明 |

**STORY-1.7 交易类型化（V2.0，P2/F）——v1.5 新增**

> As a 用户，我想转账、借出、报销这些事有各自合适的输入方式，而不是被硬塞进「支出/收入」。

按类型提供差异化界面（这是 G-6 的实现）：

| 类型 | 界面语义 | 必填差异 |
|---|---|---|
| 普通支出/收入 | 金额键盘 + 分类宫格（点分类即保存） | 分类 |
| 转账 | 转出账户 + 转入账户 + 金额（+ 手续费 + 到账金额） | 两个账户 |
| 信用卡还款 | 还款来源账户 + 目标卡 + 本期应还 + 实还金额 | 两个账户 |
| 借出/借入 | 往来对象 + 金额 + 约定还款日 + 利息 | 往来对象 |
| 报销垫付 | 金额 + 分类 + 报销标记 + 报销单号（选填） | 报销标记 |
| 报销回款 | 关联垫付单 + 实收金额 | 关联单 |

**规则**：

- 类型切换时已填金额与日期保留，分类/账户按类型重置。
- 转账类交易在流水页显示为**双行样式**（上行为去向、下行为来源），并在收支合计中计为 0（口径见 G-2）。
- **落库结构（v1.6 明确）：一笔转账 = 一条记录，含「转出账户」与「转入账户」两个账户字段**，不是两条镜像记录。
  - 该条记录计入账户余额时按**两端各算一次**（转出账户 −，转入账户 +），见 G-2.1。
  - **账户维度查询**（STORY-3.2 按账户筛选、STORY-11.3「分类 × 账户」交叉分析）时，该条**同时出现在两个账户的结果集**中，但**金额符号随账户翻转**（对转出账户显示 −，对转入账户显示 +）。因此按账户统计时不会重复计入 —— 同一笔在两个账户下是「一负一正」，合计为 0。
  - 「双行样式」是这一条记录在流水页的**渲染方式**（同一笔渲染两行），不是两条数据；编辑/删除/移入回收站**作用于这一条**，无需级联。
- **转出与转入账户不可相同**，保存时拦截并提示。

**STORY-2.2 信用卡账户（V2.0，P2/F）——v1.5 新增**

> As a 信用卡用户，我想知道这期该还多少、最晚什么时候还，这样不会逾期也不会白付利息。

信用卡账户维护**两个数字**，只让一个是权威：

| 概念 | 定义 | 可写性 |
|---|---|---|
| **欠款余额** | **存储值（可写）**；日常由 Σ 已出账未还 + Σ 未出账消费 − Σ 已还款 维护，对账时可直接修正 | **唯一权威**，与账户余额互为负值 |
| **可用额度** | 总额度 − 欠款余额 | **派生量，只读** |
| 已用额度 | 总额度 − 可用额度 | 派生量，只读 |

**配套规则**：

1. **欠款余额是存储值，不是实时聚合的派生量（v1.6 明确）**：账单入账时按上式计算并**累加写入**欠款余额字段。之所以不能做成「每次读时实时 Σ」，是因为对账需要能直接修正它 —— 若它是公式派生的，对账修正会被下一次聚合覆盖，形成循环。
2. **对账修正的是欠款余额**（直接写存储值），**同时生成一笔「对账调整」账单**作为可追溯的修正凭证（差额记为支出/收入，来源=对账，不计入收支，见 G-2）。可用额度随之自动重算（派生量手改一律被忽略并提示）。
3. **聚合校验**：对账页实时显示「按账单聚合 = X」与「当前存储值 = Y」，差额由用户确认后生成调整账单。正常无差异时两者相等。
4. **分期不自动展开**：分期是「已入账的一笔消费 + 一组待用户确认的还款计划」；用户确认后生成多期还款账单，撤销时只删未生成期数。
5. 记账不做余额校验，允许刷爆，但对超额给出橙色标记而非拦截。
6. 账单汇总只读：出账日生成的「本期应还」= 上期未还 + 本期新增 − 本期已还。

**信用卡参数**：账单日（1–28）、还款日、免息期天数（自动推导）。每笔消费显示其**免息期**（从消费日到该笔所属账单到期还款日的天数）。

AC1：Given 信用卡额度 20,000、已用 3,000，When 记一笔 500 的信用卡消费，Then 欠款余额 3,500、可用额度 16,500（派生）。
AC2：Given 用户尝试手动编辑「可用额度」，When 保存，Then 忽略该修改并提示「可用额度由欠款余额自动计算」。
AC3：Given 账单日为每月 5 日，When 6 月 8 日记一笔消费，Then 该笔归入 7 月 5 日的账单；页面显示其免息期天数。
AC4：Given 上期未还 2,000、本期新增 3,000、本期已还 1,000，When 到账单日生成汇总，Then「本期应还」显示 4,000。
AC5：Given 一笔 6,000 的消费选择 3 期分期，When 用户确认分期，Then 生成 3 期还款计划（待生成状态）；When 撤销分期，Then 仅未生成的期数被删除，已生成的逐笔进回收站。**（v1.6 补充）** When 用户从回收站恢复其中一笔已生成的分期账单，Then 该笔作为**独立普通账单**恢复（不再与分期计划关联，也不重建整条计划）。

**AC7（新增·对账直接修正欠款余额）**：Given 信用卡账单聚合应欠 3,500 而用户银行 App 显示欠 3,480，When 用户对账录入 3,480，Then 系统欠款余额直接写为 3,480、同时生成一笔 +20 的对账调整账单作为凭证、可用额度随之重算，且该调整账单不出现在本月支出统计中。

**STORY-3.3 安全可花（V2.0，P2/F）——v1.5 新增**

> As a 用户，我只想知道今天能放心花多少，而不是看一堆图表。

首页展示一个核心数字：**今天可以放心花多少**。

**计算**：

```
安全可花 = 可用资金 − 未来账单预留 − 目标待拨付 − 刚性支出预留
日均安全可花 = 安全可花 ÷ 本记账月剩余天数
```

| 项 | 定义 |
|---|---|
| 可用资金 | 现金 + 储蓄卡余额（不含信用卡额度、不含投资） |
| 未来账单预留 | 本**记账月**内周期规则待生成账单之和（见 STORY-7.3） |
| 目标待拨付 | 各储蓄/沉淀目标本记账月尚未划拨的金额（见 STORY-7.1） |
| 刚性支出预留 | 用户标记为「刚性」的分类的剩余预算 |

**「刚性支出」标记规格（v1.6 新增，定义见下）**：

- **定义**：「刚性支出」= 金额相对固定、不可推迟、不可取消的必要支出（如房租、房贷、水电、保险费）。
- **设置在分类上**：分类管理页（STORY-1.3）每个分类的编辑表单增加「标记为刚性支出」开关；同开关也在「预算」页的分类预算行提供快捷入口。**仅一级分类可标记**（二级继承所属一级的标记）。
- **存储**：`Category` 实体增加 `isRigid` 布尔字段，默认 false，随分类一并同步与备份。
- **用途**：仅用于 STORY-3.3 的「刚性支出预留」计算 —— 取所有 `isRigid=true` 的一级分类（含其子分类）在该分类预算下的**剩余预算之和**。未设预算的刚性分类不计入（无「剩余预算」可算）。
- **不影响其他口径**：该标记不改变账单的收支/分类统计归属，纯预算侧属性。

**边界**：

- 结果为负时显示「本月已超支，建议暂停非必要支出」并给出最大超支分类。
- 无预算设置时隐藏该卡片，引导用户先设预算。
- 隐藏余额模式下该数字**一并打码**（见 G-7）。
- 数字可点击展开三行拆解明细，每行可下钻到来源数据。

AC1：Given 可用资金 5,000、未来账单 1,200、目标待拨付 800、刚性预留 1,000、本月剩余 20 天，When 查看首页，Then 安全可花显示 2,000、日均显示 100。
AC2：Given 计算结果为负，When 查看卡片，Then 显示超支提示与最大超支分类。
AC3：Given 用户未设置任何预算，When 查看首页，Then 不显示该卡片，显示「设置预算后可查看今日可花」的引导入口。

### 5.4 EPIC-4 数据安全

**STORY-4.1 本地存储与手动备份**

> As a 用户，我不想注册就必须用、也不怕换手机丢数据。

数据全部本地存储（加密见 STORY-4.2），未登录可使用 100% 功能（V1.0 无账号系统）。备份：设置 → 备份与恢复（SP-4-01）→ 生成全量备份文件（含数据库快照 + 元数据版本号，本地 AES 加密，扩展名自有格式），通过系统分享导出到用户选择的任意位置（网盘/电脑）；恢复：选择备份文件 → 校验密码与版本 → 预览（账单数、时间范围、版本）→ 确认覆盖（原数据自动先生成一份「恢复前备份」）。

**v1.5 新增：备份与恢复边界**

| 场景 | 行为 |
|---|---|
| 密码错误 | 提示「密码错误」，允许重试 3 次，3 次后建议「放弃并使用其他备份文件」；不锁定、不删除文件 |
| 文件损坏 | 提示「备份文件已损坏或不完整」，尽可能展示可读出的元信息（文件大小/生成时间）；不覆盖现有数据 |
| 目标版本更高 | 拦截并提示「需要升级 App 至 X.X」，给出兼容说明 |
| 本地已有更新数据 | 恢复为**覆盖式**，但执行前必须展示「当前数据（最后账单日期 / 账单数）」与「备份文件数据范围」对比，用户确认后才覆盖 |
| 存储空间不足 | 生成前预检可用空间，不足时提示所需空间，可选「不加密直接导出」或取消 |

AC1：Given 1,000 条账单，When 生成备份，Then 文件生成 ≤ 5s，且可从该文件完整恢复到另一台设备。
AC2：Given 备份文件来自更高版本 App，When 当前版本尝试恢复，Then 拦截并提示「需要升级 App 至 X.X」。
AC3：Given 恢复操作执行，When 完成，Then 自动生成「恢复前备份」并可在备份列表中找到。
AC4：Given 用户卸载重装，When 无任何恢复操作，Then 数据为空白初始态（商店描述需写明「卸载前请先备份」）。
**AC5（新增·密码错误）**：Given 用户输入错误密码，When 校验失败，Then 提示「密码错误」且允许重试；连续 3 次失败后建议更换文件，**不删除文件、不锁定**。
**AC6（新增·文件损坏）**：Given 选择一个损坏的备份文件，When 尝试恢复，Then 提示「备份文件已损坏或不完整」且不修改现有数据。
**AC7（新增·覆盖前对比）**：Given 本地有 500 笔账单、备份含 480 笔，When 用户选择该备份准备恢复，Then 展示两者对比（账单数 + 数据范围）并要求二次确认。
**AC8（新增·空间不足）**：Given 设备剩余空间不足以生成备份，When 用户点击生成，Then 提示所需空间并提供「不加密直接导出」或取消两个选项。

**STORY-4.2 应用锁与数据加密**

> As a 用户，我不想别人拿到我手机就看到我的账。

应用锁：设置 → 应用锁，支持系统生物识别（指纹/Face ID）与数字密码；开启后冷启动与后台切前台（超过 30 秒）均需解锁；后台快照模糊（iOS 保护区遮罩 / Android FLAG_SECURE）。数据加密：本地数据库整库加密（规格约束为「拿到数据库文件无法直接读取明文」）；云传输 TLS。

**v1.5 新增：锁与生物识别的边界**

- **生物识别不可用**（设备未录入、被系统禁用、连续失败）时，**自动降级为数字密码**，不阻塞使用。
- 若数字密码也遗忘，提供「重置应用锁」入口；重置后数据仍加密，需用数据库密码解锁——**应用锁密码与数据库密码分离**。
- **小组件与锁屏**：应用锁开启且「锁定时隐藏金额」为开时，**桌面小组件与锁屏小组件一律不展示金额**（桌面小组件显示占位符，由系统进程按遮蔽态数据渲染，见 STORY-1.4 AC6）；「锁定时隐藏金额」为关时，桌面小组件可显示汇总数字（不含明细）。通知内的金额按同一开关处理。
- **后台快照**：切后台立即打遮罩（不依赖 30 秒计时）；30 秒为「需要重新解锁」的判定。

AC1：Given 应用锁开启，When App 从后台 31 秒后切回前台，Then 弹出解锁界面。
AC2：Given 应用锁开启，When 切到系统任务管理器，Then 预览为模糊/遮罩。
AC3：Given 生物识别连续失败 3 次，When 第 4 次，Then 强制回退数字密码。
AC4：Given 用文件管理器直接读取沙盒内数据库文件，Then 内容不可读（加密验证用例，开发自测项）。
**AC5（新增·立即遮罩）**：Given 应用锁开启，When 用户切到后台，Then 遮罩**立即**出现（不等 30 秒）；30 秒后切回才要求重新解锁。
**AC6（新增·生物识别不可用降级）**：Given 用户在系统中禁用了指纹，When 打开 App，Then 直接进入数字密码界面，不出现生物识别弹窗、不阻塞。
**AC7（新增·应用锁密码重置）**：Given 用户遗忘应用锁密码，When 走「重置应用锁」，Then 应用锁密码被清空、数据仍加密、需输入数据库密码后才能进入。

**STORY-4.3 隐私承诺（产品宪法）**

无广告、无开屏、不申请与功能无关权限（V1.0 仅申请：通知[可选]、照片库[可选，仅用户主动选图标上传时触发]、无其他）、不上传任何用户数据（V1.0 无任何网络数据接口，架构上以「无后端」为验收：抓包零外联业务域名，仅保留崩溃收集开关且默认关闭）。此条为 P0 硬约束，违反即验收不通过。

  - **发放形式（v1.6 明确）**：奖励以**「V4.0 权益券」**形式发放并存入「我的 → 我的奖励」，**在 V4.0 商业化上线后自动激活**（可抵扣订阅时长）。
  - **V2.0/V3.0 期间的替代激励**：因该阶段无付费产品（§2「V2.0/V3.0 不设任何付费触点」），**同时在获得时立即发放非付费类奖励**（专属徽章、限定主题/记账伙伴装扮），确保用户当下就能感知奖励。
  - **文案要求**：权益券展示时须标注「V4.0 起生效」，不得暗示当前即可使用。
- **不做**：不做积分商城、不做可兑换实物的模式、不做排行榜（记账是私事，社交比较违背隐私承诺）。

AC1：Given 用户连续 7 天每天至少记 1 笔，When 第 7 天记账完成，Then 显示「连续 7 天」成就、立即获得专属徽章并收到一张标注「V4.0 起生效」的权益券。
AC2：Given 用户已连续 15 天，When 某天未记账，Then 显示「已断签」，历史最长纪录（15 天）保留不变。
AC3：Given 用户累计记账达到 1,000 笔，When 记录完成，Then 解锁「积累」类徽章并在徽章墙展示。
AC4：Given 用户首次设置预算，When 保存完成，Then 解锁「探索」类对应徽章。
AC5：Given 用户查看成就页，When 检索是否存在排行榜或积分商城，Then 均不存在（设计约束项）。
**AC6（新增·V2.0 期间奖励可感知）**：Given 用户处于 V2.0 版本并连续记账 7 天，When 触发奖励，Then 立即生效的是徽章/装扮等非付费奖励，同时权益券入账但显示「V4.0 起生效」；When 用户点击该权益券，Then 提示其将在 V4.0 自动激活，不引导任何付费。

### 6.1 EPIC-6 自动化与交易精度

**STORY-6.1 规则引擎**

> As a 用户，我导入 500 条支付宝账单后，希望系统按我的规则自动分类，而不是手动改 500 次。

**规则结构**：

| 组成 | 说明 |
|---|---|
| 条件（IF） | 字段（金额/备注/商户/账户/分类/来源）× 运算符（等于/包含/大于/小于/介于/正则）× 值；多条件支持 AND / OR |
| 动作（THEN） | 设置分类 / 设置标签 / 设置账户 / 设置成员 / 标「不计入收支」/ 标记待报销 / 加备注前缀 |
| 执行阶段 | **pre**（导入/录入前预处理）与 **post**（导入后清理）；同阶段内按优先级顺序执行 |
| 优先级 | 整数排序，可拖动调整 |
| 适用范围 | 手动记账时 / 周期生成时 / 导入时 / 分割子笔 |

**必要能力**：

- **变更预览**：保存前展示「将命中 N 笔历史账单」，可展开查看明细，确认后才生效（默认**不回溯**已存在账单，用户可显式选择回溯）。
- **试运行**：对一条规则可「在最近 100 笔上试运行」，展示每条的结果。
- **模板化动作**：动作值支持简单模板（如备注前缀 `[报销]`）；**不做完整脚本语言**（避免复杂化与安全风险）。
- **规则列表**：可排序、启停、复制、删除。

**边界**：

- 规则冲突时按**优先级从高到低**依次施用，后者可覆盖前者的同类动作；同优先级按创建时间正序。
- 一条规则命中的账单在**执行后仍可手动修改**，手动修改**不触发**规则重跑（避免打架）。
- 正则表达式非法时保存拦截，并给出错误位置。
- 规则数量上限 200 条（防性能劣化）。

AC1：Given 用户创建规则「备注包含『星巴克』→ 分类设为 餐饮-饮料」，When 查看预览，Then 显示「将命中 12 笔历史账单」并可展开明细。
AC2：Given 用户保存该规则且选择「不回溯」，When 再记一笔备注含「星巴克」的支出，Then 分类自动设为「餐饮-饮料」；When 查看此前那 12 笔，Then 分类未变。
AC3：Given 用户保存该规则且选择「回溯」，When 确认，Then 12 笔历史账单分类全部更新，操作日志记录该次批量变更。
AC4：Given 规则 A（优先级 1）设分类为「餐饮」，规则 B（优先级 2）设分类为「餐饮-饮料」，When 两规则同时命中一笔，Then 最终分类为「餐饮-饮料」（高优先级覆盖）。
AC5：Given 用户在规则中录入非法正则，When 点保存，Then 拦截并提示错误位置。
AC6：Given 一个含 1000 笔账单的账本，When 批量套用规则，Then 耗时 ≤ 3s 且不阻塞 UI（后台 isolate）。
AC7：Given 用户对一条规则执行「试运行」，When 查看结果，Then 展示最近 100 笔中每笔的命中与动作结果，且**不修改任何数据**。
AC8：Given 用户手动修改了一笔已被规则施用的账单，When 查看该账单，Then 保留手动值，规则不重新覆盖。

**STORY-6.2 分割交易**

> As a 用户，我在超市花 300 元买了食品和日用品，希望拆到两个分类，这样统计才准。

- 一笔父交易可拆为 2–10 个子笔；每个子笔有独立分类、金额、备注、标签。
- **父笔与子笔金额必须对平**（Σ 子笔 = 父笔）；不对平时禁止保存并提示差额。
- **父/子笔的字段语义（v1.6 明确）**：账单实体新增标识字段区分「普通账单 / 拆分父笔 / 拆分子笔」。
  - **父笔**：`分类字段置空`，`不参与任何分类统计、不参与预算`，**仅作为账户变动与金额合计的载体**（账户变动由父笔计一次）。流水页父笔显示「拆分」标记与子笔数。
  - **子笔**：各自带分类，**进分类统计、进预算**，**不计账户余额**。
- 因此四处口径的过滤条件分别为：计入收支统计（父笔计、子笔不计，Σ=父笔金额）、账户余额（仅父笔）、预算统计（仅子笔）、分类统计（仅子笔）。**分类统计绝不会把父笔的那 300 再算一次**。
- 分割交易的录入走显式确认表单（G-6）。
- 支持把子笔快速「合并回父笔」（撤销拆分）。

AC1：Given 一笔 300 元的支出，When 拆为「食材 200」+「日用 100」，Then 保存成功且两分类统计各增 200 与 100（父笔不贡献分类统计）。
AC2：Given 拆分金额为 200 + 80（父笔 300），When 点保存，Then 拦截并提示「子笔合计 280，与父笔 300 相差 20」。
AC3：Given 一笔已拆分的账单，When 查看账户余额变动，Then 仅父笔金额（300）影响余额一次。
AC4：Given 一笔 300 元的分割交易，When 查看本月支出合计，Then 显示 300（不是 380）。
**AC5（新增·分类统计不双算）**：Given 上述 300 元拆分（食材 200 + 日用 100），When 查看分类统计，Then「食材」为 200、「日用」为 100，**不存在父笔的 300 落入任何分类**；When 查看全部一级分类占比合计，Then 等于 300。
AC6：Given 用户点「合并回父笔」，When 确认，Then 子笔被删除，父笔恢复为普通账单，分类为「未分类」并提示用户补充。
AC7：Given 拆分后某子笔所属分类有预算，When 查看预算进度，Then 按子笔金额计入该分类预算。

**STORY-6.3 提醒中心**

> As a 用户，我希望 App 主动提醒我还款、订阅到期和预算超支，而不是我自己去翻。

统一入口：首页顶部状态条 + 「我的」页「提醒」区块（原「发现」页入口已收进「我的」）。九类提醒：

| 提醒类型 | 触发规则 | 级别 |
|---|---|---|
| 信用卡还款日 | 到期前 3 天、当天各一次 | 响铃 |
| 订阅到期前取消 | 识别到连续扣款的订阅，在其下次扣款前 3 天提醒（可一键标记「不再需要」并给取消路径指引） | 响铃 |
| 预算分级 | 80% / 100% 各一次（每周期每分类最多各一次） | 响铃 |
| 余额不足预警 | 「安全可花」为负或某账户余额低于用户设的阈值 | 响铃 |
| 异常支出 | 单笔 > 该分类近 90 天 P90 的 2 倍（**窗口与样本口径见 STORY-5.4「共同统计口径」**），或当日合计 > 近 30 日均值 3 倍 | 静默（可升级） |
| 周期账单已入账 | 免确认入账后 | 静默 |
| 对账提醒 | 每月记账月首日提醒上月未对账 | 静默 |
| 储蓄目标待存 | 每月记账月首日 | 静默 |
| 备份提醒 | 距上次备份 > 30 天 | 静默 |

**边界**：

- 所有提醒**可逐项开关**，并提供「全部静音」总开关（默认关）。
- 夜间免打扰（默认 23:00–07:00）按 G-3 执行：响铃降级为静默，次日 08:00 汇总。
- 同类提醒**去重**（同一预算周期的同一分类最多各一次），防轰炸。
- 提醒历史可查（近 90 天）。

AC1：Given 信用卡还款日 6 月 25 日，When 6 月 22 日与 6 月 25 日，Then 各发一次响铃提醒。
AC2：Given 用户在某分类预算 1,000、已花 800，When 再记一笔 100，Then 触发 80% 响铃提醒；When 再记一笔 200（合计 1,100），Then 触发 100% 响铃提醒，共两次不重复。
AC3：Given 用户关闭「异常支出」提醒，When 发生异常支出，Then 不产生任何通知。
AC4：Given 周期账单在 23:30 免确认入账且击穿预算，When 次日 08:00，Then 收到一条汇总通知，含「已入账 N 笔」与预算预警。
AC5：Given 用户开启「全部静音」，When 任何提醒触发，Then 均不产生系统通知（仅进 App 内提醒列表）。
AC6：Given 用户查看提醒历史，When 选择近 90 天，Then 列出全部提醒（含已读/未读）与触发时间。

### 6.2 EPIC-7 预算深化

**STORY-7.1 沉淀基金 / 储蓄目标**

> As a 用户，我每年要交 3,000 元保险和 1,200 元车检，希望摊到每月，而不是到缴费时才发现没钱。

- 定义一个目标：名称 + 目标金额 + 截止日期 + 关联账户（可选）。
- 系统自动计算「每月需存入」=（目标金额 − 已存）÷ 剩余月数，并在预算页显示「本月待存」。
- 存款动作：手动「存入一笔」（生成从可用账户到目标虚拟账户的内部转账，**不计入收支**）；或开启「自动按月划拨」（走**周期规则引擎 STORY-6.1**）。
- 进度可视化：环形进度 + 剩余天数 + 逾期提示（截止日已过而未达成时标记「未达成」但保留数据）。
- 与预算结余的关系：沉淀基金是「专项预留」，预算结余是「通用结余」，二者独立计算，互不占用。

AC1：Given 创建「车险」目标 3,000 元、截止日 12 个月后，When 保存，Then 显示「每月需存 250 元」。
AC2：Given 用户在 1 月存入 250，When 查看预算页，Then「车险」目标显示已存 250、进度 8.3%、本月待存 0（本月已存）。
AC3：Given 用户存入 250 元到目标，When 查看本月收支统计，Then 收入与支出均不增加（内部转账不计入收支，见 G-2）。
AC4：Given 目标截止日已过且未达成，When 查看目标，Then 显示「未达成」标记，数据保留且可由用户修改截止日。
AC5：Given 用户本月预算已超支（负结余），When 查看沉淀基金，Then 目标进度不受影响（二者独立）。
AC6：Given 用户开启「自动按月划拨」，When 到每月记账月首日，Then 自动生成一笔划拨并产生静默通知。

**STORY-7.2 目标体系（储蓄 / 还债 / 限额）**

> As a 用户，我既想攒钱买相机，又想早点还完房贷，希望这两件事都能被追踪。

| 目标类型 | 适用 | 特有逻辑 |
|---|---|---|
| 储蓄目标 | 攒钱买物、应急金 | 进度 = 已存 ÷ 目标；可设截止日 |
| 还债目标 | 房贷、车贷、信用卡分期 | 进度 = 已还 ÷ 总欠款；含剩余期数、剩余利息、预计还清日 |
| 限额目标 | 控制类（本月餐饮 ≤ 2000） | 复用分类预算，不重复建设 |

- 还债目标与 **STORY-10.2 贷款摊销**联动：用户追加还款时，目标页显示「提前 X 个月还清、少付利息 ¥Y」。

AC1：Given 用户创建「应急金」储蓄目标 20,000，When 存入 5,000，Then 进度显示 25%。
AC2：Given 房贷还债目标总额 800,000、已还 120,000，When 查看目标，Then 显示剩余期数、剩余利息、预计还清日三项。
AC3：Given 用户对房贷目标追加一笔额外还款 10,000，When 查看目标，Then 显示「提前 N 个月还清、少付利息 ¥Z」（需已录入贷款参数，见 **STORY-10.2**）。
AC4：Given 用户创建「本月餐饮 ≤ 2000」限额目标，When 设置完成，Then 系统复用分类预算规则，不产生第二套数据。

**STORY-7.3 周期记账与规则的衔接（= 统一周期规则引擎）**

> As a 用户，我的房租、工资、会员费都是自动的，希望生成后还能被规则二次处理。

**v1.6 明确：全产品只有一套「周期调度器」（STORY-6.1 `RecurringRule` 的调度器；勿与 F1.7 的条件-动作「规则引擎」混淆），以下三类「自动生成账单」全部走它，各自带类型标识，不另建机制**：

| 生成来源 | 类型标识 | 触发锚点 |
|---|---|---|
| 周期记账（房租/工资/订阅） | `recurring` | 规则设定的锚定日（遇短月顺延月末） |
| 储蓄/沉淀目标自动划拨 | `savings_transfer` | 记账月首日（STORY-7.1 AC6） |
| 贷款每期还款 | `loan_repayment` | 每期还款日（STORY-10.2） |

- 周期生成账单时**同样适用规则引擎的 pre 阶段**（如自动补账户）与 post 阶段（如自动分类）。
- 免确认入账的通知口径走 G-3 静默；若击穿预算阈值则升级为响铃（夜间降级）。
- **系统时间被改**：周期规则按「上次执行时间 + 间隔」推进，不依赖「今天」；用户改时间到未来不补生成账单。
- **回收站恢复**：恢复周期生成的账单时保留来源标记但不恢复与规则的关联；已整体撤销的批次，其单笔不可单独恢复。
- **暂停与恢复**：规则可暂停不删除；恢复后从下一个触发点继续，不补历史。
- **修改规则**：修改金额/分类/频率后，已生成账单不变，仅影响后续。

AC1：Given 一条周期规则生成了一笔账单且存在规则「备注含房租 → 分类设为 居住-房租」，When 账单生成，Then 分类自动设为「居住-房租」（规则适用周期生成）。
AC2：Given 周期免确认账单在夜间入账并击穿某分类预算，When 次日 08:00，Then 收到汇总响铃通知。
AC3：Given 用户把系统时间改到 3 个月后，When 周期规则触发，Then 不批量补生成账单，仅在下一个真实触发点生成一笔。
AC4：Given 用户从回收站恢复一笔周期生成的账单，When 查看该账单，Then 来源标记保留，但不再与该周期规则关联。
AC5：Given 用户暂停某周期规则，When 暂停期间到达触发点，Then 不生成账单；When 恢复，Then 从下一个触发点继续，不补历史。

### 6.3 EPIC-8 数据与同步（V2.0）

**STORY-8.1 官方云同步**

> As a 用户，我想手机和平板的数据自动一致，不想手动传文件。

- 账单级采用基于共同祖先的三方合并（3-way merge）；无共同祖先或字段冲突时取最后写入并生成冲突副本，用户在「冲突中心」裁决。
- 同步范围：账单、分类、账户、账本、预算、周期规则、标签、成员、报销单、储蓄目标、规则、商户学习记录（完整清单见下表）。
- 同步延迟目标 ≤ 10 秒（同账号活跃端）。

**同步范围完整清单**（这是 STORY-5.2 约束 3 与《01》F7.2 的落地）：

| 类别 | 项目 | 是否同步 |
|---|---|---|
| 数据资产 | 账单、分类、账户、账本、预算、周期规则、标签、成员、报销单、储蓄目标、规则、商户学习记录 | **同步** |
| 数据资产 | 账单附件 | 不同步（V2.0/V3.0 均不） |
| 可同步设置 | 月起始日、隐藏余额、字体大小、音效、保存后停留、提醒开关 | **同步** |
| 本地偏好 | 主题、外观模式、首页卡片布局、记账页布局偏好 | **不同步** |

判定原则：**描述「数据是什么」的同步；描述「这台设备怎么看数据」的不同步**。

AC1：Given 手机与平板均已开启同步，When 手机新增一笔账单，Then 平板在 10 秒内可见。
AC2：Given 两端同时修改同一笔账单的不同字段，When 同步完成，Then 自动合并（3-way merge）且不产生冲突副本。
AC3：Given 两端同时修改同一字段为不同值，When 同步完成，Then 生成冲突副本，两端在「冲突中心」可见并可裁决。

**STORY-11.1 预算方法论切换**

|---|---|---|

AC1：Given 用户当前用「自定义」，When 切换到「信封法」，Then 预算页按信封呈现，各类独立滚存，且给出切换前后的对照预览。

AC4：Given 用户切换到「50/30/20」，When 查看预算页，Then 按需/想要/储蓄三档展示，并显示各自实际占比与目标占比的偏差。
AC5：Given 用户切换方法论前后，When 查看历史账单与历史报表，Then 数据完全不变。
**AC6（新增·限额目标跨方法论保留）**：Given 用户在「自定义」下有 3 个限额目标，When 依次切换到信封法、零基法、50/30/20，Then 这 3 个限额目标在每套方法论下均可查看并继续参与校验，不丢失、不重复。

AC6：Given 500 个节点的数据量，When 渲染，Then 耗时 ≤ 800ms。

**STORY-11.3 多维度交叉分析**

> As a 用户，我想看「标签 × 月份」或「成员 × 分类」这类交叉表。

- 输出：矩阵表（行=维度 A，列=维度 B，单元格=金额）+ 可切换热力着色。
- 可保存为「我的报表」（保存筛选与维度组合，一键复现）。

AC1：Given 用户设置「行=分类，列=月份」，When 应用，Then 生成矩阵表且单元格金额正确。

AC4：Given 用户保存为「我的报表」，When 下次进入，Then 一键复现该组合。

**STORY-11.4 资金年龄（Age of Money）**

> As a 用户，我想知道我赚的钱能撑多久才花掉。

- 定义：**当前花掉的每一块钱，其来源收入距今天数的加权平均**。
- 算法（FIFO）：把每笔收入按时间排队，每笔支出消耗最早未消耗的收入，支出日与所耗收入日的差值即该笔支出的「资金年龄」，按金额加权平均。
- 展示：一个数字 + 近 6 个月趋势线 + 一句话解读。
- 边界：数据不足 2 个月或收入笔数 < 5 时显示「数据积累中」；存在负值时取 0 而非负数。

AC1：Given 用户有完整 6 个月数据，When 查看资金年龄，Then 显示一个数字与 6 个月趋势线。
AC2：Given 用户上月记为「先花后收」（某笔支出早于最近收入），When 计算，Then 该笔年龄取 0 而非负数。
AC3：Given 用户仅有 1 个月数据，When 查看，Then 显示「数据积累中」。
AC4：Given 用户查看解读文案，When 资金年龄为 43 天且上月为 35 天，Then 文案为正向表述（如「比上月更从容」）。

**STORY-11.5 税务 / 可抵扣支出报表**

- 用户可给分类或标签标记「可抵扣」。

- 支持标记「已申报」状态。

AC2：Given 用户选择「2026 年度」，When 生成报表，Then 按类别列出可抵扣支出与合计。
AC3：Given 用户标记某月报表为「已申报」，When 再次查看，Then 显示「已申报」状态并可取消。

### 7.3 EPIC-12 协作深化

**STORY-12.1 家庭协作深化**

> As a 家庭用户，我想知道哪笔是我的、哪笔是共同的，也想对某笔账单留句话。

- **交易归属标记**：每笔账单可标「我的 / TA的 / 共同的」，家庭视图可按归属筛选与统计。
- **交易级评论**：成员可对任意账单留言，对方在流水页看到评论角标。
- **独立登录**：每个成员独立账号；权限与数据归属按账号区分。
- **只读分享**：可生成只读链接/邀请码给财务顾问或长辈，仅可查看不可编辑，可随时撤销。
- **AA 分摊细化**：一笔账单可标记参与人（多选）与分摊方式（均分 / 自定义金额 / 比例），系统自动计算每人应付与净额，并生成「成员间结算建议」（谁该给谁多少钱）。

**边界**：成员退出时其名下账单保留（不删除），归属改为「已退出成员」（成员记录软删除，见 STORY-8.2）；账本至少有 1 名管理员，最后一名管理员不可退出（须先转让）。

AC1：Given 一笔账单被标记为「共同的」，When 按「共同的」筛选，Then 该笔出现在结果中。
AC2：Given 成员 A 对一笔账单留言，When 成员 B 查看流水，Then 该笔显示评论角标，点开可见留言。
AC3：Given 一笔 300 元账单标记 3 人按比例 1:1:1 分摊，When 查看，Then 每人应付 100。
AC4：Given 一笔账单标记参与人为 A、B，When 查看结算建议，Then 显示「B 应付 A ¥N」这类明确指令。
AC5：Given 唯一的成员退出，When 尝试退出，Then 拦截并提示「请先转让管理员」。
AC6：Given 生成了只读分享链接，When 访问者尝试编辑，Then 只读，且管理员可随时撤销链接。

> ⚠️ **遗留一处潜伏不一致（`split_role` 维度，V1.0 收尾建议修）**：增量入口用 `countsInCategoryStats`（**父笔不计**），但 `ledger_repository` 的 **`verifyDailyStats()` / `rebuildDailyStats()` 过滤条件为 `type IN ('expense','income') AND source <> 'reconcile'`，缺 `split_role != 'parent'`**。对同一笔分割交易，增量写 1 份（仅子笔）而巡检/重建数 2 份（父 + 子）→ 巡检恒判「不一致」→ 每次冷启动触发全量重建 → 重建把父笔也算进 `daily_stats`（**父笔被双算**）。当前 `split_editor_page` 未接线、无 UI 生成分割笔，故为**潜伏缺陷**；一旦分割交易可创建即显形。修法：两处 SQL 各补 `AND split_role <> 'parent'`，无需 schema 变更。

**第六条数据侧硬约束（v1.6 新增）：金额上限以代码常量为准**

金额上限由 `core/money/money.dart` 的 `Money.maxCents = 9999999999`（单位为**分**，即 **99,999,999.99 元**）统一约束，判定入口 `Money.withinProductLimit`。UI 输入控件与预算/周期规则仓储的写入校验都引用该常量，**改上限只改一处**。文档若出现其他数值（如 `999,999,999.99`）均为换算笔误，以代码为准。

**兼容性**：iOS 15+ / iPadOS 15+ / Android 8.0+（API 26）/ Android Pad 含 2GB 内存档（降级：关动画、报表惰性渲染）；**v1.5 新增**：macOS 13+、现代浏览器（Chrome/Edge/Safari 最近两个大版本）。

**多端**：四端（iOS/iPadOS/Android/Android Pad）UI 响应式从 V1.0 贯彻，数据模型与业务逻辑层全端共享。V3.0 增加 Web/macOS 端。**平板不是「放大的手机」**——形态变化的方向是「更高信息密度 + 多栏」。断点、布局壳、页面规约与验证矩阵见《07-屏幕适配方案.md》。

**可用性**：离线全功能；数据库 schema 迁移向前兼容（升级不丢数据）。

**合规**：

- 个保法最小必要；V1.0 无账号故无注销需求，V2.0 账号体系上线时注销与数据删除为上架前置条件。

**质量**：核心业务逻辑单测覆盖 ≥ 70%（口径：行覆盖率，统计范围为共享内核，见《05》§8.3）；崩溃率 ≤ 0.1%；同步冲突自动解决率 ≥ 95%；AI 识别准确率 ≥ 95%（金额与日期字段，内测集口径）；20 套主题配色对比度校验零失败。**v1.5 新增**：V3.0 净值可追溯率 100%（每项资产/负债均可下钻到明细）。

**无障碍**：20 套主题配色的对比度校验为 CI 必过项（正文 ≥ 4.5:1、大字与图形 ≥ 3:1，WCAG AA）；收支方向不得仅靠颜色区分，须同时有 +/− 符号；字体三档缩放不破版。

## 12. 风险与依赖（需求侧）

**需求变更风险**：V2.0/V3.0 范围显著扩大（新增 26 条需求），最大风险是「范围过大导致延期」。应对：每条需求已标注复杂度；**规则引擎、云同步、投资持仓、桌面端**为四个最大块，各自独立排期与验收；每版本末做「砍范围不砍质量」的复盘。

**商业化节奏风险**：商业化后移至 V4.0 意味着中期无收入。应对：V2.0/V3.0 严控成本（短信、行情等需外部依赖的功能先预研）；留存与口碑数据作为 V4.0 招商与投资依据；V4.0 上线即带完整付费理由。

**技术依赖**：本地优先 + 后置同步的架构约束必须在 V1.0 第一周确认，否则 V2.0 云同步改造成本指数级上升。

**架构替换被低估的风险（v1.7 新增）**：V2.0 的云同步是**从「整库文件替换」到「change_log 字段级增量合并」的架构替换**（《04》§6.5），含合并引擎、冲突中心 UI、后台调度、GC 与位点联动四个子系统；**若按"把文件同步换成增量同步"估算工作量，V2.0 必然延期**。应对：立项时单列 EPIC，与规则引擎并行启动。

**加密与性能的取舍风险（v1.7 新增）**：SQLCipher 在低端 Android 上若超出 200ms 落库预算，需回到产品层在「接受变慢 / 只加密敏感列并下调 C6 表述 / 自研加密层」之间拍板（《01》开放问题 #10），**不得静默降级**。

**外部依赖**：App Store 审核周期（IAP 相关 V4.0 才涉及）；投资行情源合规与稳定性；短信权限审核；商店编辑推荐无承诺性，营销计划按自然流量做基线。

**竞争风险**：咔皮系大厂 AI 免费玩家若在窗口期内上四端，差异化组合需收敛到「数据自由」单一强主张。
