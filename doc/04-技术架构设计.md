## 1. 架构目标与硬约束

架构的第一职责是把 PRD 里的约束变成不可违反的结构，而不是画一张好看的图。以下七条是硬约束，冲突时以序号小者优先。

| # | 约束 | 来源 |
|---|---|---|
| C1 | 四端（iOS/iPadOS/Android/Android Pad）共享数据模型与业务逻辑，UI 差异只在视图层 | PRD §8 多端 |
| C2 | 本地优先：V1.0 零后端、无账号、离线全功能 | PRD F7.1、STORY-4.3 |
| C3 | 同步可后置插入，且**不得改造业务写入路径** | PRD §11 技术依赖 |
| C4 | schema 迁移向前兼容，升级不丢数据 | PRD §8 |
| C5 | 性能红线：冷启动 ≤1.5s、落库 ≤200ms、万条流水 60fps、报表 ≤1s、包体 ≤40MB | PRD §8 |
| C6 | 数据库文件离线不可读 | PRD STORY-4.2 AC4 | `[已满足]` **SQLCipher 已接入**：`pubspec.yaml` 的 `hooks.user_defines.sqlite3.source: sqlcipher` + `PRAGMA key` 校验；见 §10 |
| C7 | 平台独有能力（小组件、隐私遮罩）隔离在明确边界内，不渗入业务层 | v1.0 新增 |

**架构风格**：分层 + feature-first 垂直切片，单向数据流。

C3 是本文档存在的核心理由。PRD §11 已判定「V2.0 云同步改造成本指数级上升」的风险，控制手段只有一条：**V1.0 就把变更日志（change_log）写进每一条写入路径**，哪怕当期没有任何消费者。第 6 章展开。

依赖方向严格单向：①→②→③，③←④（依赖倒置），④→⑤。**③ 不得依赖任何外层**，这是四端共享与可测试性的物理保证。

### 架构守卫（CI 自动拦截，不靠自觉）

四条规则写成 lint 脚本进 CI，违反即构建失败。架构文档的效力全在能否被机器执行。

1. `lib/domain/**` 与 `lib/core/money/**` 不得出现 `import 'package:flutter/`
2. `lib/features/<A>/**` 不得 import `lib/features/<B>/**`；跨 feature 通信一律经 domain 用例
3. `lib/features/**/presentation/**` 不得 import `lib/data/**`（只允许依赖 domain 接口）
4. 业务写入不得直连 DAO：`txnsDao.insert(` 只允许出现在 `lib/data/repositories/` 内

## 5. 数据层设计

### 5.1 金额：int64「分」，永不使用 double

- 存储与运算一律 `INTEGER`（分为单位），显示层格式化。任何金额参与 `double` 运算即为缺陷。
- 上限 99,999,999.99 元 = 9,999,999,999 分，int64 有充分余量（无溢出风险）。
- 表达式求值（`12.5+7.5 → 20.00`）在 domain 的 `ExpressionEvaluator` 内以「分为单位的整数 + 定点小数步进」实现，四则运算用整数化约分，不引入浮点。
- V2.0 多币种汇率精度 10^8 定点整数。

### 5.2 主键：UUID v7（TEXT, 26 字符）

三个理由，任一成立即足够：时间有序（B-tree 插入局部性好，万条流水分页稳定）、全局唯一（V2.0 多端合并必需）、**V1.0 定下就无需后期迁移**——主键类型变更是灾难级迁移，这是典型的「一次做对」项。

### 5.3 V1.0 建表范围：功能可以后置，数据形态必须一次到位

| 类别 | 内容 | 决策 |
|---|---|---|
| 业务表 | transactions / categories / accounts | V1.0 建 `[已实现]` |
| 审计表 | change_log / app_meta | V1.0 建 `[已实现]` |
| **派生表** | daily_stats | V1.0 建（可全量重建，不参与同步，见 §5.5）`[已实现]` |
| **V2.0 功能预留表** | budgets / recurring_rules / **rules** / **savings_goals** / **merchant_rules** | **V1.0 已建表并全链路实现**（表 + 索引 + 实体 + 仓储 + 用例 + UI，见《08》§5.7/§5.8）`[已实现]`；功能产品归属仍为 V2.0 |
| 未上线实体 | books / conflict / sync_meta / ai_quota | V1.0 **不建**，随对应版本迁移脚本新增 |
| 审计字段 | 软删除、revision、device_id、base_revision | **V1.0 全量落地，不可省** `[已实现]` |
| 业务语义字段 | `source` 来源枚举、`batch_id` 周期批次 | 挂各自业务表，**不属审计字段** `[已实现]` |
| 业务语义字段 | `split_role` 拆分角色、`parent_id` 父笔 ID、`reimburse_status` 报销状态、`reconciled_at` 对账时间、`is_rigid` 刚性支出标记 | **2026-10-15 更新：均已落列** `[已实现]`（`kSchemaVersion = 11`）；⚠️ 其中 `is_rigid` 与 `accounts.credit_debt_cents` **尚未被业务逻辑消费**，语义层仍属 V2.0 |

判断依据：空表不产生收益却增加迁移与测试负担，故不建；但审计字段属于数据形态而非功能——PRD §7 已判定「来源」枚举与软删除/同步版本号事后补历史数据成本极高，且 change_log 一旦晚做就要改造全部写入路径。**功能可后置，数据形态不可后置。**

> **三处澄清（对齐《08》v1.3 与代码实况）**：
>
> 1. **审计字段与业务语义字段是两件事。** 审计字段（软删除 `deleted_at` / `revision` / `device_id` / `base_revision`）是**跨表统一的同步与生命周期基础设施**，每张权威表都有；而 `source`（账单来源）、`batch_id`（周期批次）、`split_role` / `parent_id`（分割交易父子结构）、`is_rigid`（分类刚性标记）是**某一张表特有的业务语义**，只有持有它的表才有这些列（`source` / `batch_id` 仅 `transactions` 持有）。二者混为一谈会让「审计字段清单」变成大杂烩。字段级定义以《08》§4.2 / §5.1 / §5.2 为准。
> 2. **代码实际建 11 张表**（业务 3 + 设备本地 2 + 派生 1 + V2.0 预留 5），完整分类与「是否参与同步 / 是否写 change_log / 是否可重建」见《08》§1。
> 3. **✅ `split_role` / `parent_id` / `is_rigid` / `reimburse_status` / `reconciled_at` 均已落列**（2026-10-15 复核，`kSchemaVersion = 11`）。上一版本（2026-10-09）把这三列记作「代码中不存在、`kSchemaVersion` 仍为 3」——**该结论已过期，此处更正**。其判据（《08》§2「后补需触碰历史行」）依然成立，只是三列已在 v3→v11 迁移过程中补齐。

### 5.4 索引与查询策略（万条 60fps 的实现来源）

- **keyset 分页，禁用 OFFSET**：游标 = `(occurred_at, id) DESC`。OFFSET 在万条量级随页数线性劣化。
- 部分索引处理软删除，避免全表带过滤条件：

```sql
-- 列表主查询：记账月区间 + keyset 分页
CREATE INDEX idx_entry_book_time   ON transactions(book_id, occurred_at DESC, id DESC) WHERE deleted_at IS NULL;
-- 分类下钻、分类合并、报表按分类聚合
CREATE INDEX idx_entry_category    ON transactions(category_id, occurred_at DESC)      WHERE deleted_at IS NULL;
-- 账户余额聚合、账户删除前的引用检查
CREATE INDEX idx_entry_account     ON transactions(account_id, occurred_at DESC)       WHERE deleted_at IS NULL;
-- 转账入账方向：按「转入账户」查（单行双向模型，见《08》§5.1）
CREATE INDEX idx_entry_to_account  ON transactions(to_account_id, occurred_at DESC)    WHERE to_account_id IS NOT NULL AND deleted_at IS NULL;
-- 周期生成批次：整批撤销（V1.0 已建）
CREATE INDEX idx_entry_batch       ON transactions(batch_id)                           WHERE batch_id IS NOT NULL;
-- 分割交易父笔展开（2026-10-15 补：列已落列）
CREATE INDEX idx_entry_parent      ON transactions(parent_id)                          WHERE parent_id IS NOT NULL;
-- 分类二级下钻 / 一级含其二级聚合
CREATE INDEX idx_category_parent   ON categories(parent_id);
-- 账户排序、change_log 实体查询、预算/周期/规则归属
CREATE INDEX idx_account_sort      ON accounts(sort_order);
CREATE INDEX idx_change_entity     ON change_log(entity_type, entity_id);
CREATE INDEX idx_budget_book       ON budgets(book_id);
CREATE INDEX idx_recurring_due     ON recurring_rules(next_run_at);
CREATE INDEX idx_recurring_book    ON recurring_rules(book_id);
CREATE INDEX idx_rule_book         ON rules(book_id);
-- 唯一约束（同名去重 / 防重复预算）
CREATE UNIQUE INDEX uq_category_name ON categories(COALESCE(parent_id, ''), name);
CREATE UNIQUE INDEX uq_account_name  ON accounts(name);
CREATE UNIQUE INDEX uq_budget_total  ON budgets(book_id)     WHERE scope = 'total';
CREATE UNIQUE INDEX uq_budget_category ON budgets(book_id, category_id) WHERE scope = 'category';
```

> **索引总数（2026-10-15 复核）：17 条 `CREATE INDEX` 语句**（13 条普通索引 + 4 条唯一索引），完整清单见《08》§6。

> **索引清单以《08-数据模型设计》§6 为准。** 两点修正：
>
> - **`idx_entry_parent` 已存在**（2026-10-15 更正）：随 `transactions.parent_id` 落列一并建立，用于分割交易的父笔展开。上一版本记为「已移除、列不存在」，结论过期。
> - 早前的 `idx_change_seq ON change_log(local_revision)` 已删除——`local_revision` 改为 `INTEGER PRIMARY KEY AUTOINCREMENT`（SQLite 的 rowid 别名，本身即主键索引），再建普通索引纯属冗余写放大（见 §6.1 与《08》§5.4）。

- 列表渲染使用固定 `itemExtent`，规避滚动期布局测量。
- 关键词筛选（V3.0 高级筛选）用 FTS5 虚拟表，**列为验证项**：SQLCipher 构建需确认已启用 FTS5（见 14 风险）。

### 5.5 统计聚合：物化表增量维护，杜绝报表全量扫表

报表 ≤1s 与首页秒开都依赖这一点。原则：**写入时付小代价，读取时不付代价。**

> **字段级定义以《08-数据模型设计》§5.6 为准。** 08 将聚合表由「按月」细化为**按日记账日粒度**（`daily_stats`），比按月粒度多覆盖一处 PRD 需求（报表页的「月收支结余走势」需按日折线），且**使得「月起始日变更」不再需要全量重算**——记账月边界退化为查询期的日区间。理由与权衡见《08》§7.3。

- 表：`daily_stats(book_id, day_key, category_id, account_id, expense_cents, income_cents, tx_count, updated_at)`
- 写一笔账单时，与账单插入**同事务** upsert 受影响的行，成本约 1 次索引写。
- 报表页只做 SQL 聚合与排序，不把明细拉进 Dart 内存计算。
- 派生表不参与同步（V2.0 合并由权威表驱动），且必须可全量重建（见《08》§8）。
- **聚合口径（PRD G-2 / G-2.0）**：`expense_cents` / `income_cents` 只累计「计入收支统计」的账单——**必须排除对账调整与分割交易子笔**；分割交易的父笔计一次（分类置空，不进分类维度）。按分类聚合时另需过滤「进消费/分类统计 = 是」。完整 8 行口径表见《08》§7.3，代码侧须抽成 **领域常量**由查询与写入共用，不得两处各写一遍过滤条件。

### 5.6 迁移与备份

- **手写 schema 版本 + 逐步迁移**（`data/db/database.dart` 的 `kSchemaVersion` 与 `_migrate()`；**不使用 Drift 的迁移框架**）；**每个历史版本保留一份数据库快照夹具**，CI 中执行「安装旧版 → 升级 → 校验数据完整」回归。这是 C4 的唯一可靠保证。**当前 `kSchemaVersion = 11`（11 表 / 17 索引）**，实际迁移步见《08》§9.1。
- 备份（`core/backup/backup_container.dart`，**已实现**）：`VACUUM INTO` 生成一致性快照 → 封装为 `SUJIBAK2` 容器（魔数 + SQLCipher 库字节），备份体用 SQLCipher `rekey` 到用户备份密码（**复用同一加密引擎，不另做 AES-GCM**）；无 SQLCipher 时回退 `SUJIBAK2P`（口令校验 + 原样封装）。恢复：`extractBackupDb` 解出明文临时库 → 覆盖前自动生成「恢复前备份」（PRD STORY-4.1 AC3 / AC5）。PBKDF2-HMAC-SHA256（100k 轮）保留用于口令校验。
- 并发：**当前为单 isolate 同步 sqlite3 调用**——全项目尚无 `Isolate.run` / `compute` 使用点。⚠️ 这与 v1.0 规划的「后台 isolate 执行、UI isolate 不做 SQL 解析」**不一致**，是已识别的性能风险（万条量级报表聚合可能卡帧），列为 V1.0 收尾项，见 §14 风险 8。

## 6. 同步预留架构（本文档最关键章节）

### 6.1 变更日志（change_log）：V1.0 写入，V1.0 不消费

**所有写入路径唯一入口是 Repository，事务内同时提交业务表与 change_log。** 这是 C3 的落地点。

```
写用例 → Repository → BEGIN
                       ├─ INSERT/UPDATE transactions
                       ├─ UPSERT daily_stats        （派生表，同事务增量维护）
                       └─ INSERT change_log
                     COMMIT
```

`change_log` 字段：

| 字段 | 说明 |
|---|---|
| `local_revision` | 本设备单调递增序号，**`INTEGER PRIMARY KEY AUTOINCREMENT`**（rowid 别名，天然单调、无断层、无需外部计数器） |
| `entity_type` / `entity_id` | 变更对象 |
| `op` | insert / update / delete |
| `device_id` | 设备标识 |
| `base_revision` | **本次修改所基于的版本** → V2.0 三方合并的共同祖先指针 |
| `payload` | **变更后的实体字段快照**（JSON）→ V2.0 字段级三方合并的数据来源；仅有哈希无法逐字段比对 |
| `payload_hash` | 幂等去重与冲突检测辅助 |
| `changed_at` | 变更时刻 |

> `local_revision` 由 `AUTOINCREMENT` 提供而非 `app_meta` 计数器维护：计数器方案需要「读—加—写」且必须与业务写同事务，多一次写放大且易在异常路径下产生断层；`AUTOINCREMENT` 由 SQLite 保证严格单调递增、不复用已删除的号。字段级定义以《08》§5.4 为准。

**V1.0 行为**：只写不读。GC 策略为保留 30 天且单表上限 5 万行，超出按 `local_revision` 删最旧。

为什么 GC 不影响 V2.0：设备首次接入云同步时本来就要走「全量基线 + 增量」的快照同步，历史 change_log 并非必需；它的价值在于 V2.0 起有消费者（WebDAV / 官方云）之后，增量同步链路是现成的。**代价 30 天窗口换 V2.0 零改造，这笔交易很划算。**

**`change_log` 的写入实况 `[已实现]`**：`data/sync/change_log_writer.dart` 按上述字段写入，`payload = {"before": …, "after": …}`，`payload_hash = sha256(payload)`，`entryPayload()` 覆盖 18 个字段。

> ⚠️ **与当前同步实现的偏差（必须记录）**：`data/sync/webdav_sync_service.dart` 实现的是**整库文件同步**——上传用 `VACUUM INTO` 生成一致性快照后传整个 `.sqlite` 文件，下载则直接替换本地 `plain.sqlite`。**它完全不消费 `change_log`。** 因此本节描述的是 **V2.0 的目标架构**，当前 WebDAV 入口是**过渡实现**。
>
> 整库替换在多端并发写入时会**直接丢数据**（后上传者覆盖先上传者），**不可作为 V2.0 的正式同步方案**。从「整库替换」升级到「change_log 驱动的字段级增量合并」是一次**架构替换而非增量开发**——这也意味着 `change_log` 的 `payload` / `base_revision` 这笔 V1.0 前置投入的价值不变（它是增量合并的唯一数据来源），但**V2.0 的工作量不能按「只换传输层」估算**。

### 6.2 同步通道抽象：可插拔

```dart
abstract interface class SyncProvider {
  Future<PushResult> push(List<ChangeRecord> batch, SyncCursor since);
  Future<PullBatch>  pull(SyncCursor since);
  ProviderCapability get capability;   // 是否支持服务端 3-way merge
}
```

| 实现 | 版本 | 备注 |
|---|---|---|
| `WebDavProvider` | **V2.0**（免费差异化） | 先落地。会把 change_log 消费链路跑通。**当前已有过渡实现**：`WebDavSyncService` 走整库文件同步（见 §6.1 偏差说明） |
| `ICloudProvider` | V2.0（iOS） | 文件通道，复用 WebDAV 的合并逻辑 |
| `OfficialCloudProvider` | V2.0（主付费点） | 仅换传输与服务端裁决，客户端合并逻辑复用 |

> ⚠️ **代码实况**：`data/sync/sync_provider.dart` 中的 `SyncProvider` 抽象及其 6 个相关类型**目前是孤儿代码**——只有自引用，无实现、无消费者（实际走的是 `WebDavSyncService`，它不实现 `SyncProvider`）。这是**为 V2.0 预留的接口骨架**，本身无害，但真实同步路径与抽象不匹配；V2.0 落地时需二选一：让 `WebDavSyncService` 实现该接口，或删除该抽象。**不要误以为「同步通道抽象已就绪」。**

**路线图顺序对架构有利**：V2.0 用 WebDAV 验证同步骨架，官方云只是换通道 + 接入服务端，而非从零开发。这也把 PRD §11 的「同步后置风险」实际降级为「增量交付」。

### 6.3 冲突裁决

- 字段级三方合并：`base_revision` 定位共同祖先，逐字段比对，非冲突字段自动合并。
- 无共同祖先或字段冲突：两版本都保留，生成冲突副本，进入「冲突中心」由用户裁决（PRD F7.2）。
- 自动解决率目标 ≥95% 的达成前提是**大多数写入是「新增」而非「同字段并发修改」**，这与记账类产品的写入分布吻合。

### 6.4 硬约束

业务代码中**不得出现任何「如果在线就上传」的分支**。同步是独立消费者（后台任务/调度），只在 change_log 上工作。违反此条即退回第 2 章守卫规则。

### 6.5 V2.0 同步升级路径：整库替换 → change_log 增量合并

**这是一次架构替换，不是传输层替换。** 本节把升级拆成可验证的阶段，避免在 V2.0 开工时低估工作量。

**现状与危害（V1.0）**：

`WebDavSyncService` 的两条路径：
- **上传**：`VACUUM INTO 'sync_upload_<ts>.db'` → 读字节 → `put` 到 WebDAV
- **下载**：`get` → 校验 SQLite 文件头 → `close()` 本地库 → 备份为 `.bak` → `copy` 覆盖 `plain.sqlite` → 提示「请重启应用」

| 危害 | 说明 |
|---|---|
| **多端并发直接丢数据** | 设备 B 下载了设备 A 的快照后，A 若再写入并上传，B 的下载副本丢失；反向亦然。**后上传者覆盖先上传者**，无合并、无冲突提示 |
| **下载后必须重启** | `close()` 后 Db 句柄失效，UI 无法继续用；当前靠提示用户手动重启 |
| **`change_log` 闲置** | 18 字段 `payload` + `sha256` + `base_revision` 已写入，但无消费者 |

> 结论：整库替换**只能作为「单端备份/迁移」用途**（如换机、离线拷贝），**不可作为 V2.0 的多端同步方案**。

**已就绪的 V1.0 前置投入**（升级时可直接用）：

| 组件 | 位置 | 状态 |
|---|---|---|
| `change_log` 写入 | `data/sync/change_log_writer.dart` | ✅ 全写路径接入 |
| `payload = {before, after}` | 同上 | ✅ 字段级 diff 的数据来源 |
| `base_revision` 祖先指针 | 同上 | ✅ 三方合并定位共同祖先 |
| `local_revision` `AUTOINCREMENT` | `database.dart` | ✅ 天然单调、无断层，可直接当游标 |
| `device_id` 设备标识 | `app_meta['device.id']` | ✅ 不随备份迁移 |
| `change_log_repository` 读取 | `data/repositories/change_log_repository.dart` | ◐ 已有查询方法，未接入同步流 |

**缺口（必须在 V2.0 补齐）**：

| # | 缺口 | 说明 |
|---|---|---|
| 1 | **`SyncProvider` 无实现** | `sync_provider.dart` 是孤儿代码（§6.2），`WebDavSyncService` 不实现它 |
| 2 | **无 `conflict` 表** | 「两个版本都保留」需要落地位置（《08》§10） |
| 3 | **无 `sync_meta` 表** | 同步位点（各设备 last seen `local_revision`）需要持久化（《08》§10） |
| 4 | **无裁剪策略** | 当前 `change_log` GC 为「30 天 / 5 万行」，但**同步位点可能小于 GC 窗口**——GC 前必须确认所有已知设备已消费到更早的位点，否则永久丢变更 |
| 5 | **无后台任务** | 同步应跑在后台 isolate（与 §14.1 路径 B 同源） |
| 6 | **无服务端裁决能力探测** | `ProviderCapability`（是否支持服务端 3-way merge）未实现 |

**分阶段迁移路径**：

| 阶段 | 目标 | 可验证的退出标准 |
|---|---|---|
| **S1 接口收口** | 让真实同步路径实现 `SyncProvider`（或删抽象） | `WebDavSyncService implements SyncProvider`；`push` / `pull` 签名确定 |
| **S2 拉取（只读）** | 用 `local_revision` 游标 `pull` 远端 change_log（**不改本地**） | 能把远端变更解析成 `ChangeRecord` 列表；断点续传（`sync_meta` 记录位点） |
| **S3 三方合并（单字段）** | `base_revision` 定位祖先 → 逐字段比对 → 非冲突自动合并 | 新增类变更多端合并正确；冲突进入 `conflict` 表而非覆盖 |
| **S4 冲突中心 UI** | 冲突副本展示与用户裁决（PRD F7.2） | 自动解决率 ≥95% 基准可测 |
| **S5 推送 + 后台化** | `push` 本地未上传变更；同步跑后台 isolate | 万条变更同步不卡 UI；多端并发不丢数据（S3 的最终验收） |
| **S6 GC 与位点联动** | GC 前校验所有设备已消费 | 位点小于 GC 窗口时**禁止裁剪**并告警 |

**改造面提示**：S3 的字段级合并需要**每张权威表的字段清单**（《08》§4.2 已有）；`daily_stats` **不参与同步**（派生表，两端各自维护，§6.1 硬规则）；`app_meta` 的 `device.id` **不同步**。这些都是 V1.0 已定的约束，升级时不得违反。

**工作量定性**：S1–S6 是一个完整子系统的开发（合并引擎 + 冲突 UI + 后台调度 + GC 联动），**不能按「把文件同步换成增量同步」估算**。建议在 V2.0 立项时单列 EPIC。

## 8. 关键流程与性能实现

### 8.1 记账落库路径（预算 ≤200ms）

```
点分类
 → Controller 求值表达式（domain，<1ms）
 → CreateEntryUseCase：校验 + 生成 UUIDv7 + 补齐审计字段
 → 单事务：insert transaction + upsert daily_stats + insert change_log（<30ms；加密写为 V2.0 变量）
 → 提交返回 → toast + 金额清零（帧内反馈 <16ms）
 → 异步：widget snapshot 更新 + 统计缓存标记（不阻塞交互）
```

关键点：**UI 反馈不等待任何派生工作**。widget 刷新与缓存失效都在事务提交后异步触发，这是「3 秒记一笔」体感的实现基础。

**实况说明**：落库路径已按上述实现（`CreateEntryUseCase` + `LedgerRepositoryImpl.insert` 单事务写三处）。**对账调整同样走 `CreateEntryUseCase`**（`source = EntrySource.reconcile`），不再有直连 DB 的旁路写入——早前代码审计中「绕过 change_log 与 daily_stats」的 P0 缺陷已修复。**SQLCipher 已接入**（§10），`<30ms 含 SQLCipher 加密写` 这一预算在真机低端机型上的复测仍待补（见 §15 数据层专项验证包）。

### 8.2 冷启动路径（预算 ≤1.5s，中端 Android）

| 阶段 | 预算 | 手段 |
|---|---|---|
| 原生启动 → 引擎就绪 | 300–450ms | 启动期不初始化无关原生 SDK |
| `main()` → 首帧 | ≤400ms | **`main()` 内 await 上限 2 次**：主题偏好、数据库句柄 |
| 首帧后数据就绪 | ≤400ms | 首页查询走索引 + 物化表；其余初始化延后 |

**启动期禁止清单**：启动动画、网络请求、全量统计查询、图标字体全量加载、插件批量 `await`（最常见的性能杀手）。

允许延后到首帧后的：生物识别状态探测、图标库懒加载、统计预热、widget 同步、诊断包检查。数据首帧必需（小组件可直达记账页，需读分类），因此 DB 句柄前置但**只开句柄不做全量查询**。

### 8.3 报表加载（≤1s）

SQL 聚合 + 惰性渲染 + 结果缓存（缓存键 = `book + month + 月起始日`）。环形图下钻为二次聚合查询（按 `category_id` 分组），不预拉全量明细。

## 10. 安全设计

> ✅ **首要事实（2026-10-15 代码复核）**：**SQLCipher 全库加密已接入。** `pubspec.yaml` 的 `hooks.user_defines.sqlite3.source: sqlcipher` 选用加密构建，`@Native` 直接绑定 SQLCipher（**无需 `open.overrideFor`**）；`data/db/database.dart` 在开库时执行 `PRAGMA key = x'HEX'`，并以 `PRAGMA cipher_version` 做运行时自检（原生 sqlite3 不返回该值，见 `test/change_log_gc_test.dart`「native lib exposes SQLCipher cipher_version (C6)」）。数据库文件落盘为密文。
>
> **因此 C6（数据库文件离线不可读）当前已满足。** 剩余待办仅为**加密性能维度**的测量（万条量级下 SQLCipher 相对明文 sqlite3 的开销），不影响正确性；见 §10.1 与《01》§8.1。

### 10.1 数据库加密方案对比（**已决策：方案 A 已落地**）

> ✅ **2026-10-15 复核**：下方对比为**决策依据存档**。**已按方案 A 落地**，但与当时的「落地步骤」规格有四处出入，以代码为准：
> ① 未引入 `sqlcipher_flutter_libs`，改走 `pubspec.yaml` 的 `hooks.user_defines.sqlite3.source: sqlcipher`（`@Native` 直接绑 SQLCipher，**无需 `open.overrideFor`**）；
> ② 密钥走 **blob 形式** `PRAGMA key = x'HEX'`（非 `'xxx'` 文本形式），原因是历史库按 blob 加密，换形式会 `hmac check failed`；
> ③ 运行时自检用 `PRAGMA cipher_version`（原生 sqlite3 不返回，可据此判定加密是否生效）；
> ④ 备份**不是**「快照仍是加密库、key 相同」，而是 `SUJIBAK2` 容器 + `rekey` 到用户备份密码（见 §10 第 6 项）。
> **当前待办收敛为一项：加密性能实测**（第 3 条约束 200ms 落库预算 + §14 风险 1）。

**约束事实**（决定取舍的三个前提）：

1. 当前是**裸 `sqlite3` 3.6 + 手写 DDL/迁移**，`AppDatabase` 持有一个 `Database _db`（`data/db/database.dart:12`），所有读写都经它。**换加密驱动 = 换这一个类的打开方式**，仓储层无需改动——这是最有利的一点。
2. **同步是整库文件同步**（`VACUUM INTO` 生成快照上传 / 下载替换 `plain.sqlite`）。加密必须让**"快照文件"与"运行时文件"加密口径一致**，否则下载下来无法打开。
3. **落库预算 200ms**（§8.1），低端 Android 是底线。

| 维度 | 方案 A：SQLCipher | 方案 B：应用层加密 |
|---|---|---|
| **做法** | 引入 `sqlcipher_flutter_libs`（+ `sqlite3` 的加密构建），打开库时 `PRAGMA key = 'xxx'`；已有明文库首次打开执行 `PRAGMA rekey` | 不改 DB 驱动。对敏感列（`note` / `amount_cents`? / `name`）在仓储层做 AES-GCM 加解密 |
| **改动面** | **小**：`AppDatabase.open()` 换驱动 + 加一次 `PRAGMA key`；`rekey` 迁移步一次 | **大**：每个读写点都要加解密；所有 SQL 层聚合/排序/`LIKE`/索引**全部失效**（金额求和、日期排序、分类名唯一索引都要重做） |
| **包体** | +约 2–4 MB / ABI（SQLCipher so） | 近零（`crypto` 已在依赖里） |
| **性能** | 有加密开销，但落在 C 层；**须在低端机实测 200ms 落库预算** | 单列加密开销小，但聚合查询退化为全表拉取后内存计算，万条量级会崩 |
| **备份/同步兼容** | 快照经 `VACUUM INTO` 后**仍是加密库**（同一 key），上传/下载天然一致 —— **与现架构最契合** | 备份文件里是密文列，恢复依赖同一 master key；且同步按行合并时密文无法做字段级 diff（V2.0 冲突判定的灾难） |
| **密钥管理** | 32 字节随机 passphrase 存 `flutter_secure_storage`；用户忘记应用锁密码**不丢数据**（key 在安全存储，非密码派生） | 若用密码派生 key，忘记密码 = 数据永久丢失；若用随机 key，同样存安全存储 |
| **PRD C6 满足度** | **完全满足**（文件级不可读） | 部分满足（文件结构暴露，仅列值加密）——**不足以宣称「离线不可读」** |
| **对 V2.0 同步的影响** | 无额外负担 | **严重阻碍**：字段级三方合并需比对明文 |
| **风险** | ① 低端机性能；② 需验证 FTS5 可用性（§14 风险 2）；③ `sqlcipher_flutter_libs` 与现有 `hooks` 镜像下载机制的配合 | ①②③ 额外：破坏所有索引/聚合，等于重写数据层 |

**推荐：方案 A（SQLCipher）**。理由收敛为一条——**B 与「本地优先 + 派生聚合 + 即将字段级同步」这三条产品底座正面冲突**，而 A 只动一个类。

**落地步骤（✅ 已执行，与规格出入处已按代码更正）**：

1. ~~`pubspec.yaml` 加 `sqlcipher_flutter_libs`~~ → 实际用 `hooks.user_defines.sqlite3.source: sqlcipher`（`@Native` 直绑，无 `overrideFor`）。
2. ✅ `AppDatabase.open()` 保留 `sqlite3.open(path)`，随即 `PRAGMA key = x'HEX'` 并执行一次 `SELECT count(*) FROM sqlite_master` 触发校验（key 错则 `file is not a database`）；`_cipherAvailable()` 以 `PRAGMA cipher_version` 判定加密运行时是否就绪。
3. ✅ 密钥来源：`loadOrCreateDbPassphrase()` 生成 32 字节随机值 → `flutter_secure_storage`（+ 会话缓存防「开库 key ≠ 导出 key」）。
4. ✅ 明文库升级：`_tryOpenEncrypted()` 已实现——检测到既有明文库时 `PRAGMA rekey = x'HEX'` 就地转换后重开（见 `database.dart:59-77`）。
5. ⚠️ **与规格不同**：备份/恢复**不靠**「快照仍是加密库、key 相同」，而走 `SUJIBAK2` 容器 + `rekey` 到用户备份密码（见 §10 第 6 项）。
6. **验收**：①-③ 已具备（密文库 + 备份恢复闭环）；② 低端 Android 落库 ≤200ms、④ 冷启动不劣化 **仍待实测**。

**若 A 的性能不达标**：退路不是 B，而是**「敏感列加密 + 全库加密延后到 V2.0」**，并同步下调 PRD C6 的表述（须产品确认），因为 B 的改动面与同步冲突不可接受。

### 14.1 长查询迁后台 isolate 评估（风险 8）

**实况**：全项目 `Isolate.run` **0 处**、`compute(` **0 处**（2026-10-09 全 `lib/` 扫描）。所有 SQL 均在 UI isolate 同步执行——`sqlite3` 的 `select` / `execute` 是**同步阻塞调用**，且 `data/db/database.dart` 持有的单连接被 UI 与（未来的）后台共享。

**热点清单**（按影响排序）：

| # | 位置 | 查询 | 量级 | 影响 |
|---|---|---|---|---|
| 1 | `ledger_repository` | 流水列表全表扫描 + 排序（`ORDER BY occurred_at DESC LIMIT ?`） | 万条 | 首帧与滚动 |
| 2 | `ledger_repository` / `account_repository` | `SUM` 聚合（月合计、账户余额 5 段式） | 万条 | 切月、进资产页 |
| 3 | `reports_page` | `daily_stats` 日聚合 + 环图切片构建 | 千～万 | 报表页 |
| 4 | `csv_importer.dart` | CSV 解析 + 批量插入 | 万行 | 导入时卡死 UI |
| 5 | `preset_categories` / 统计重建 | 全表遍历 | — | 冷启动、恢复后 |

**关键约束（决定方案可行性）**：**`sqlite3` 的 `Database` 连接对象不可跨 isolate 传递。** `sqlite3.dart` 的 `Database` 是绑定到创建它的 isolate 的原生句柄，被另一个 isolate 使用会崩或未定义行为。因此不能简单「把 `_db` 传给 `Isolate.run`」。

**三种可行路径**：

| 路径 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 查询在后台 isolate 内自开连接** | `Isolate.run(() => sqlite3.open(path)..select(sql))`；主 isolate 只收结果 | 真并行，UI 不卡 | 每次开连接有开销；WAL 下可多连接，但**写路径仍须回主 isolate 串行**，否则锁竞争 |
| **B. 专用「DB isolate」常驻** | 起一个长期 isolate 独占连接，UI 通过 `SendPort` 发请求/收结果（类似 sqflite 的隔离模型） | 一次开连接、请求排队、写读都串行在专用线程 | 改造面最大，等于自建一层 DB 服务；需处理生命周期与错误传播 |
| **C. 只迁纯计算** | 把**已从 DB 取出的行**做后处理（排序、分组、金额计算）放进 `Isolate.run` | 零 DB 约束、零锁竞争、改动最小 | 只解决 CPU 部分，I/O 仍在 UI isolate |

**推荐：先 C、后按需升级到 B。**

- **V1.0 收尾**：采用 **C** 处理 `reports_page` 的切片构建与排序、`csv_importer` 的解析段——这两处是纯 CPU，改动小、风险低，能挡住最明显的掉帧。
- **V1.0 后 / V2.0**：若实测万条仍卡（尤其导入），升级到 **B**（专用 DB isolate）会一次性解决 I/O；这同时是**同步从整库替换升级为 change_log 增量合并（风险 9）时的必要基建**——增量同步本身就是长任务。
- **A 不推荐**：每次开连接 + 多连接写竞争，收益不抵复杂度。

**验收标准**：① 万条流水滚动稳定 ≥55fps；② 报表切换首帧 ≤100ms；③ 万行 CSV 导入期间 UI 无可见卡顿（进度可更新）；④ 落库总耗时不变（迁 isolate 不得因序列化往返而劣化）。

**注意**：`perf_benchmark_test.dart` 已存在但**未进 CI 门禁**（§11）。评估落地前应先把该基准接入 CI，否则无法回归验证。

### 16.1 设计令牌规格

#### 16.1.1 双层结构

令牌解析链：`ThemeId → (ToneId, BrandPalette[light|dark], TonePalette[light|dark]) → 派生出前景/语义/图表类 → ThemeData`。

- **中性层（TonePalette）**：底色、卡片、文字、分隔线等与色相无关的层。按 3 种基调分化——`cool`（冷，青绿系主题用）、`warm`（暖，暖色系主题用）、`neutral`（无彩，素白用）。每基调含 `light` / `dark` 两态。
- **品牌层（BrandPalette）**：主色（primary 系）与强调色（accent 系）两条色阶，每主题独占。浅色态与深色态各定义一套（深色态不是浅色态的机械反转，须单独取值并各自过校验）。
- **明暗**：由「外观偏好 × 平台亮度」解析，不由主题决定。切换主题不改变明暗，切换明暗不改变主题。

**透明度政策（三级，不得越级使用）**：

| 层级 | 取值 | 适用 | 理由 |
|---|---|---|---|
| 结构色 | **必须不透明** | `bg` `appBg` `surface` `surface2` `ink` `muted` `line` 及全部品牌/语义基色 | 半透明结构色的实际渲染色取决于其下叠了什么——同一令牌在不同位置呈不同颜色，且对比度无法静态校验，820 项门禁会整体失效 |
| 淡彩层 | **品牌色 + alpha** | `primary-soft`(16%·深色 26%)、`primary-tint`(10%·16%)、`accent-soft`(16%·26%) | 「空气感」的载体：淡彩底随所处底自适应，视觉更轻盈。**代价是校验必须按合成后的实际色进行**，故派生走 `inkForLayers()`（§16.1.6 ①′） |
| 装饰层 | **真 alpha** | 光斑、有色阴影、遮罩、Toast 底、渐变端 | 不承载文本，无对比度义务（本就用 `rgba()`） |

> **语义淡彩层（`income-soft` / `ok-soft` / `warn-soft` / `dn-bg`）保持不透明**：语义色须跨主题恒等，半透明化会让同一个「红」在 10 套主题的不同底色上呈现不同结果，破坏 INV-1 与用户读表习惯。通透感优先让给品牌层。

#### 16.1.6 派生算法规格

实现放在**无 Flutter 依赖**的纯 Dart 文件（便于单测与 CI 复用）。以下为契约级规格：

```dart
// 相对亮度 / 对比度（WCAG 2.1）
double lum(int argb);
double contrast(int a, int b);          // (max+0.05)/(min+0.05)

// 在 sRGB 上向黑/白线性混合，保持色相沿亮度轴推进
int mix(int a, int b, double t);
```

**① `inkFor(fg, bg, target)` —— 彩色小字态**

若 `contrast(fg,bg) ≥ target` 直接返回 `fg`；否则按 t=0.05…1.0 步进，向黑或白推进，返回首个达标值。

**方向判定必须用两端极值**：`toBlack = contrast(black, bg) > contrast(white, bg)`。

> ⚠️ 禁止用中间灰（如 t=0.3）的探针判方向——中间调背景下探针会落进对比度低谷从而判反方向（上一代配色的浅色强调色 `#4E8B80` 曾因此卡在 3.94:1）。任意背景下 `max(白, 黑)` 对比度恒 ≥ 4.58:1，故该写法**必有解**。

**①′ `inkForLayers(fg, layers, target)` —— 彩色小字的「最不利底」（实际调用入口）**

彩色小字会落在多种底上（页面底 / 机身底 / 卡片 / 两档淡彩的叠合色）。**必须对全部可能底取最不利者**：

```dart
int inkForLayers(int fg, List<int> layers, double target) {
  final probe = inkFor(fg, layers.first, target);
  final toDark = lum(probe) < lum(layers.first);      // 方向由探针判一次
  final ref = layers.reduce((a, b) => toDark
      ? (lum(b) < lum(a) ? b : a)                     // 暗字 → 取最暗底
      : (lum(b) > lum(a) ? b : a));                   // 亮字 → 取最亮底
  return inkFor(fg, ref, target);
}
```

> ⚠️ **只对单一底（如淡彩底）派生必漏**——本轮实测漏 19/820 项：浅色态**页面底比卡片暗**，深字在其上对比更低（青瓷 4.49、杏黄 4.14）；深色态**高 alpha 那档淡彩比卡片亮**，亮字在其上对比更低（青瓷 3.81）。两个方向各有一个死角，必须一起纳入。

**② `pickOn(bg, deep, target)` —— 实心色块前景色**

优先级：主题墨色 `deep` → 纯白 → 交给 `inkFor()` 继续推进。用于 `--on-primary` / `--on-accent`。

> 现行配色的主色多为高饱和中明度（Tailwind 500 档），与白字的对比多数不足 4.5:1，故实心主色块（chip 选中、勾选点）与强调块（FAB、保存键）**多数自动翻深字**，由 `pickOn` 判定，无需逐套指定。

**③ 强调渐变 `accentSheen`**

`sheen = mix(a, onAccent == white ? black : white, 0.12)`，渐变取 `linear-gradient(sheen → a)`。

> 含义：渐变只朝「远离明暗分界」的一侧展开，使两端对比度**均不劣于**纯强调色端（该端已被 `pickOn` 保证达标）。禁止向分界另一侧过渡——两端会落在分界两侧，数学上无解。

**④ `heroSafe(c)` —— 结余卡渐变压暗（兜底，正常不触发）**

hero 渐变**恒配白字**。若 `contrast(white, c) < 4.6`，按步进向黑混合直至 ≥ 4.6。

> 本轮配色换代后，hero 两端已在**设计期**用同一判据迭代到白字 ≥ 4.75:1（见 §16.1.4 表），故运行时基本不触发压暗，浅色主题的结余卡不再变沉。**该函数保留为兜底**：后续任何改色仍受它保护，不必重新人工核对。

**⑤ 其余派生**

`chart-track = mix(surface2, p, dark ? 0.18 : 0.10)`；`bar-fill = mix(appBg, p, dark ? 0.42 : 0.36)`；`dash = mix(line, muted, 0.42)`；光斑与有色阴影用 `rgba(p|a, α)`，α 随明暗取值。

> 淡彩层由 CSS 自行合成（`rgba(p, α)` 叠在所处底上）。**在 sRGB 分量上做线性插值即为浏览器的 alpha 合成算法，因此 `mix(surface, p, α)` 与浏览器实际渲染色逐位一致**——这是「校验值 = 渲染值」成立的前提，勿改用线性光空间混合。

#### 16.1.7 Material 3 ColorScheme 映射

Flutter 内置组件（SnackBar、Dialog、Switch、Chip、TextField 等）从 `ColorScheme` 取色，必须显式映射，否则深色态会出现「白底白字」类缺陷：

| ColorScheme | 取令牌 |
|---|---|
| `surface` / `onSurface` | `--surface` / `--ink` |
| `surfaceContainer*` | `--bg` / `--surface-2`（按层级） |
| `primary` / `onPrimary` | `--primary` / `--on-primary` |
| `secondary` / `tertiary` | `--accent` / `--accent`（强调色仅用于关键动作） |
| `outline` / `outlineVariant` | `--line` / `--line-soft` |
| `error` / `onError` | `--income` / `--on-accent` 同族派生 |
| `scaffoldBackgroundColor` | `--app-bg` |
| `brightness` | 由外观偏好 × 平台亮度解析 |

**`ColorScheme.fromSeed` 不适用**：种子算法产出的色阶不受本变更控制，无法保证 20 套对比度达标。主题必须由**显式色值构造**。

### 16.2 数据与持久化

#### 16.2.1 存储方案与 key

按《08》§3 结论，V1.0 **不建权威表**，走《06》C1 的平台偏好存储。仅两个 key：

| Key（建议名，随 C1 定稿的前缀约定调整） | 类型 | 取值 | 默认 |
|---|---|---|---|
| `pref.theme.id` | String | 10 个 ThemeId 之一 | `subai`（默认主题） |
| `pref.theme.mode` | String | `system` / `light` / `dark` | `system` |

**序列化只存 2 个字符串，不存任何色值**——色值是编译期常量，落盘会导致升级后配色与新版本不一致（历史脏数据）。读取时若值不在枚举内即回落默认。

外观三态直接映射 Flutter 内置 `ThemeMode`，**不要自造枚举**。

#### 16.2.2 首帧时序（不闪屏）

《06》B1 已定：`main()` 内 `await` 上限 2 次，**主题偏好是其中之一**。时序要求：

1. `runApp` 之前同步读出 `themeId` / `themeMode`；
2. 首帧即以目标主题构建 `MaterialApp`；
3. 平台侧启动图（launch screen）使用中性底色，避开「浅→深」跳变；
4. 偏好读取失败或被阻断时，走默认值继续启动，不得阻塞启动。

#### 16.2.3 云同步排除（V2.0 衔接）

同步设置的序列化 payload **不得包含** `themeId` / `themeMode`（INV-3）。理由已在《01》F9.2 写明：手机深色、平板浅色是合理组合，同步会互相覆盖。V2.0 建 `settings` 表时，把这两个 key 明确排除在同步范围之外，并在表注释中写明原因。

#### 16.3.4 组件使用规范

1. **只准使用语义令牌**，禁止 `Color(0x...)` / `Colors.*` / 直接色值（INV-5，《05》C2 已有此条，本次为强制执行）。新增 lint 或 arch_guard 规则扫描 `lib/features/**` 与 `lib/design_system/**`。
2. **`ThemeData` 必须缓存**：20 种组合（10 主题 × 2 明暗）在首次访问时构建并缓存为不可变实例，切换时只做引用替换。**禁止在 `build` 内做颜色运算**——这是「≤100ms」与「不闪屏」的实现前提。
3. **切换不重建页面**：只替换 `MaterialApp.theme`，不改 `navigatorKey` / 根 Widget 的 `key`，不重跑 bootstrap；Navigator 栈、滚动位置、输入中状态须保留。
4. 强调色只用于关键动作（FAB、保存键），不做全局染色；`--faint` 仅用于非文本装饰。

#### 16.3.5 平台边界

**系统栏。** 主题/明暗变更时同步 `SystemChrome.setSystemUIOverlayStyle`：状态栏与导航栏图标亮度随 `Brightness`；Android 建议 edge-to-edge，由页面底色透出，避免硬编码栏色造成主题割裂。

**桌面小组件（对应 AC8）。** Flutter 无法直接给 WidgetKit / AppWidget 上色，需经既有 platform 通道传值：

- App 侧在主题或明暗变更后写入「当前机身底 / 主色 / 强调色 / Brightness」4 项；
- iOS 存 App Group `UserDefaults`，Android 存 `SharedPreferences`（供 AppWidget 读取）；
- 写入后立即请求刷新时间线（`WidgetCenter.reloadAllTimelines` / `AppWidgetManager.notifyAppWidgetViewDataChanged`）；
- **小组件跟随 App 主题，不跟随系统亮暗**（AC8 要求强调色与 App 内一致）。

V1.0 若小组件尚未交付，此通道的 key 契约与写入逻辑仍应按上述落地，小组件上线时直接消费。

## R2 数据刷新（强制架构）

- **写 → bump**（`ref.invalidateData.bump*`），**读 → watch**（`xxxVersionProvider`）。
- 读模型统一 **FutureProvider**；禁止页面 pop 手动 `_load()`。
- 实现：`core/refresh/data_invalidation.dart`。**这是架构上最值得保持的一项**（单向刷新、零违规）。

## R3 仓储写路径

- 统一 **`runWrite`**：事务 + change_log + `Result`；`on Object` 防 Error 漏网（**已修正早期只捕 `Exception` 导致事务悬挂的缺陷**）。
- 软删 / 物理删 / merge 均写 change_log；物理删见 `hardDelete` / `purgeExpired`。
- ⚠️ **features 层越层写 SQL 已大幅收敛**：`.raw.` 调用在 `features/` 仅剩 **8 处 / 4 文件**（`entry_input_page` 2 / `reports_page` 2 / `backup_page` 2 / `sync_page` 2），较 v1.2 记录的 34 处（含 `accounts_page` 12）显著下降——**`accounts_page` 现已零直连**。`design_system` 层零违规。残余部分仍违反架构守卫规则 4，**列为 V1.0 收尾技术债**。

## R4 主题（替代 BrandColors）

- **`AppColors`（ThemeExtension）** 挂在 `ThemeData.extensions`；UI 用 **`context.colors`**。
- 10 套品牌色 × 亮暗，走 `theme_resolver` 的 20 条缓存；对比度门禁 `tool/theme_contrast_check.dart`（820 项）。
- 分类色 `categoryColorMap` 以 **iconRef** 为键（改名不失效）——《12》§8.1 的 `name`→`key` 迁移**已完成**。
- ⚠️ **双轨未收敛**：`design_tokens.dart` 的 `BrandColors` 静态门面仍在（约 25 文件 248 处），它读模块级可变全局，与 ThemeExtension 并行；常驻 widget 须手动 `watchBrandTheme(ref)` 补刷新。另有 `ThemeModeOption` 全家为死代码。
